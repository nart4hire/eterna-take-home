# tech_spec.md — requirement → implementation → tests

StockFlow, mapped against the numbered requirements in [`project.md`](project.md) (§4.1 Authentication,
§4.2 Inventory, §4.3 Invoices, §4.4 Frontend, §5 Non-functional).

**How this file was produced.** The table below was first built by independent discovery: the
requirements were read from `project.md`, and the implementation and test columns were derived by
reading the source tree, the API route handlers, the Prisma schema/migration and the test suites
(`tests/unit`, `tests/integration`) — without consulting `implementation_plan.md`, the task cards or
the execution graph. Only afterwards was the result cross-checked against those planning documents,
and every disagreement is recorded in [`docs/discrepancies.md`](docs/discrepancies.md). The
discovery columns are the useful ones: they describe what the code actually does.

**Columns.** *Requirement* — the ID from `project.md` plus a one-line restatement. *Implementation* —
where the behaviour lives, as `path` and the symbol/function that carries it. *Tests* — the suite,
file and test title that pins it, or the manual evidence when no automated test can exist (the UI has
no browser suite by the user's AMEND-T04-1 decision, so F1–F6 and the git-history check are verified
by checklists and inspection, never claimed as automated tests).

## Cross-check with the planning documents

After the table above was written from the code alone, it was compared against
`implementation_plan.md` (the 36-ID traceability matrix), `docs/execution/dependency-graph.json`
(`requirements` per task, `acceptance_records`), the eleven task cards and the memory bank. Points
where the two descriptions disagreed, or where a claim could not be confirmed, are recorded in
[`docs/discrepancies.md`](docs/discrepancies.md) — including the ones that turned out to be wording
rather than defects, so the record is honest about both. The per-requirement evidence ledger with
revisions and results is [`docs/requirements.md`](docs/requirements.md).

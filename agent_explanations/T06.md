## 1. Summary

StockFlow gains an owner-scoped **invoice draft** HTTP API: create a multi-line draft from current
product data, list/filter/paginate your invoices, read one invoice with its snapshotted lines, and
atomically replace a draft's whole line set under a version guard. All money is computed
server-side in integer cents with a single half-up tax step; drafts never reserve stock; every
query is scoped to the session user. 28 real-PostgreSQL integration tests cover the task's
requirement IDs: V1, V2, V3, V4, V5, V9, V10, A6, A7, N6.

## 3. Architecture and mental model

The existing layering is unchanged — thin Next.js Route Handler → `requireAuth` (BetterAuth session
from headers) → owner-scoped service → Prisma/PostgreSQL, with T02's shared Zod contracts
(`lib/validation/schemas.ts`), `lib/money.ts`, `lib/http.ts` error/DTO helpers and T01's
`withSerializableRetry`. T06 adds no layer and no dependency; it is the invoice-shaped instance of
the pattern T05 established for products.

```
POST /api/invoices
 └─ requireAuth(headers)                 → 401 even for malformed input        (A6)
 └─ assertSameOrigin(request)            → 403 for missing/foreign Origin     (A6/N6)
 └─ readJson(createInvoiceSchema)        → 400 non-JSON / 422 field errors    (N6, V1)
 └─ createInvoice(userId, input)
      ├─ readEnv(process.env).taxRateBps                                     (V3)
      └─ withSerializableRetry(tx)
           ├─ snapshotItems  → owned+active products, stock check, snapshots (V1, V4, V5)
           ├─ calculateTotals(snapshots, rate)                               (V2)
           └─ tx.invoice.create({ ..., items: { create: snapshots } })
```

Three ideas a newcomer needs: a **snapshot** is the product's `name`/`unitPrice` copied onto the
line at write time so later product edits cannot rewrite history; a **draft** is still editable and
reserves **no** stock; the **version** column is optimistic concurrency control — every write
increments it and a stale writer gets `409`.

## 4. Implementation walkthrough

### 4.1 `lib/services/invoices.ts` (213 lines)

**Boundary types and mappers (12–99).** `InvoiceRow` and `ItemRow` are structural types that omit
`userId`; `toSummaryDto` / `toItemDto` / `toDetailDto` are the only exits to HTTP, so "never
serialize `userId`/`deletedAt`" is enforced by construction rather than by convention.
`dateOnly()` renders `@db.Date` values as `YYYY-MM-DD` and `toStoredDate()` parses `YYYY-MM-DD`
back to a UTC-midnight `Date` — the timezone-drift guard the plan asked for.

**Error factories (43–60).** `notFound` (404 invoice), `productNotFound(index)` (404 **plus**
`fields["items.<i>.productId"]`), `insufficientStock(index, available, name)` (409
`INSUFFICIENT_STOCK`, message names the product), `versionConflict` (409 `VERSION_CONFLICT`),
`notEditable` (409 `INVOICE_NOT_EDITABLE`). They are `AppError`s, so `lib/http.ts:errorResponse`
turns them into the standard body with `cache-control: no-store`; a Prisma `P2034` exhaustion is
mapped structurally to `409 TRANSACTION_CONFLICT` by that same helper.

**`generateInvoiceNumber(id, createdAt)` (90–93)** returns `INV-<UTC year>-<uuid>`. The service
generates the UUID itself (line 160) so the number exists before insert and can never collide the
way `count+1` would under concurrency.

**`snapshotItems(tx, userId, lines, existing)` (113–131)** — the heart of the task:

1. `loadOwnedProducts` (103–106) performs a single `findMany({ id: { in: productIds }, userId, deletedAt: null })`,
   so foreign, unknown and soft-deleted products are simply absent from the map (indistinguishable,
   no information leak) and no split-line trick can bypass the guard.
2. Per line, in request order: missing product → `productNotFound(position)`;
   `quantity > quantityOnHand` → `insufficientStock(...)`.
3. Only then is the snapshot chosen: an existing line on this invoice keeps its stored
   `productName`/`unitPrice`, otherwise the product's current values are used;
   `lineTotal = unitPrice * quantity`, `position = index`.

Because the ownership lookup happens first, re-submitting a soft-deleted product is rejected rather
than silently re-snapshotted — the plan's "a draft containing a deleted product cannot issue; it
must remove or replace that line" rule.

**`listInvoices` (133–148)** mirrors T05: `orderBy [{createdAt: "desc"}, {id: "asc"}]` for a
deterministic tie-break, `skip`/`take` from the strict query schema, and `count` under the same
`where` (status filter included), returning the flat `Page` envelope.

**`getInvoice` (150–154)** is `findFirst({ where: { id, userId }, include: { items: { orderBy: { position: "asc" } } } })`
and 404s when absent; ownership lives in the `where`, not in a post-hoc comparison.

**`createInvoice` (157–187)** — order matters:

- `readEnv(process.env).taxRateBps` runs **before** the transaction, so a bad `TAX_RATE_BPS` fails
  with nothing written.
- `randomUUID()` and `createdAt` are computed **outside** the retry callback, so a `P2034` retry
  re-runs the same insert with the same id and the same number.
- One transaction: snapshots → `calculateTotals` → a single `create` with nested `items.create`.
  No `Product` write anywhere, which is exactly why a draft reserves no stock.

**`replaceInvoiceItems` (189–212)** — also order-sensitive:

1. Load the owned invoice with its items ordered by position.
2. Three distinct rejections before any computation: no row → 404; `status !== "DRAFT"` → 409
   `INVOICE_NOT_EDITABLE`; `version !== input.version` → 409 `VERSION_CONFLICT`.
3. Snapshots against `invoice.items` (retained snapshots) and totals against `invoice.taxRateBps`
   (the stored rate, never a fresh env read).
4. `updateMany({ where: { id, userId, status: "DRAFT", version: input.version }, data: { ...totals, version: { increment: 1 } } })`
   — the race-safe claim.
5. `invoiceItem.deleteMany` + `createMany` — whole-set replacement in the same transaction, so a
   failing insert rolls the delete and the version bump back together.

### 4.2 The three route modules (38 / 25 / 28 lines)

Intentionally uniform: `requireAuth` **first** (so malformed input still yields 401), then
`assertSameOrigin` on mutations, then strict-body parsing, then one service call.
`parseId` is a six-line duplicate of T05's helper (deliberate: `lib/http.ts` is T02-owned and shared
helpers require coordinator coordination) and turns a malformed UUID path segment into
`422 VALIDATION_ERROR fields.id`, while a well-formed but unknown/foreign id is the service's 404.
`readQuery` parses `URLSearchParams` through the same strict `invoiceListSchema`, which is why
`?sort=createdAt` is a 422 instead of being silently ignored. Every handler exports
`runtime = "nodejs"`; responses are `no-store`.

### 4.3 Happy path, traced end to end

Products A = 1299¢ (10 on hand), B = 999¢ (4 on hand). `POST /api/invoices` with
`items: [{A,3},{B,2}]`, `customerName: "Acme Distributors"`, `issueDate 2026-09-01`,
`dueDate 2026-09-30`, `notes: "Net 30"`:

| Step | Result |
|---|---|
| Snapshot | `A: 1299×3 = 3897`, `B: 999×2 = 1998`, positions 0 and 1 |
| Totals | `subtotal 5895`; numerator `5895×1100 = 6484500` → `floor(648.45) = 648`, remainder `4500 < 5000` so no round-up; `taxAmount 648`; `total 6543` |
| Stored | `status DRAFT`, `taxRateBps 1100`, `version 0`, `invoiceNumber INV-<year>-<uuid>` |
| Response | 201 with the detail DTO (summary + items), `cache-control: no-store` |
| Side effects | product stock still 10 and 4 — nothing reserved |

These are the numbers the suite asserts (`tests/integration/invoices.test.ts:236`), not
illustrative arithmetic. Note the draft reports `total` *including* tax while `subtotal` is
pre-tax — both fields are explicit, so no consumer has to infer the convention.

## 5. Correctness, edge cases and security

**Validation and bounds.** `createInvoiceSchema` / `replaceInvoiceItemsSchema` are pre-existing T02
strict objects (`z.strictObject`; `items` 1–100 with a `superRefine` duplicate check;
`calendarDateSchema` rejecting `2026-02-30`; `dueDate >= issueDate`). Unknown keys are 422, so a
client injecting `subtotal`, `total`, `taxRateBps`, `status`, `userId`, `invoiceNumber`, `unitPrice`,
`productName` or `lineTotal` gets field-level 422s. Arithmetic is integer-only with
`lineTotal`/`subtotal`/`total ≤ 2147483647` and tax rounded **once** half-up on the subtotal
(`lib/money.ts:46`). A max-price product (`2147483647¢`) overflows at the line with `× 2` and at the
*total* with `× 1` once the 11% tax is added — both are `422 ARITHMETIC_BOUNDS`.

**Ownership and information hiding.** `userId` is part of every `where`, so a foreign invoice is a
404 and never "exists but forbidden", and a foreign/unknown/deleted **product** reference is 404 as
well (plan: "another user's identifier returns 404, including nested product references"),
distinguished from a plain invoice 404 only by `fields["items.<i>.productId"]`.

**Precision.** No float anywhere on the money path; `unitPrice × quantity ≤ 2.1e15` stays a safe
integer even before the bounds check, so `assertBounded` never sees a silently corrupted product.

**Transactions and concurrency.** Both write paths use `withSerializableRetry` (Serializable, only
`P2034` retried, 3 attempts, rethrow for T02's mapper). Two concurrent same-version replacements
cannot both win: one commits (`version` 1) and the other either retries into a stale-version
`VERSION_CONFLICT` or exhausts into `TRANSACTION_CONFLICT`. The `count === 0` branch is
belt-and-braces, since under Serializable a concurrent write surfaces as `P2034` rather than a stale
read.

**Stock: validated, never reserved.** No draft path writes `Product`; `quantityOnHand` is re-read on
every create/replace, so an intervening stock reduction turns a later edit into
`409 INSUFFICIENT_STOCK`. That is exactly the "line you can no longer fulfil" state T07 will have to
resolve at issue time.

**Atomicity.** Validation precedes every write and the writes share one transaction, so an invalid
*second* line leaves the original item row, `version`, and totals untouched — proven by the suite,
not inferred.

**Hygiene.** `no-store` on every response, sanitized 500s (an invalid `TAX_RATE_BPS` leaks no
configuration value), and no `userId`, hash, session token or cookie ever reaches a DTO.

**Not applicable (do not infer coverage):** status transitions, terminal states, stock
deduction/restoration, cancellation overflow, UI/auth redirects, rate limiting.

## 7. Findings, limitations and open decisions

The read-only review pass produced the items below; the same list lives in the card's "Review
findings and discrepancy log", which is where the coordinator's rulings should be recorded.

**Corrections already applied to the card** (worker-owned): the push-status line equated the tested
revision (`09dffee`) with the remote tip (`3103517`); "origin/main did not advance" was true only for
the first round; T04 was described as "still unreviewed at dispatch" although it is now DONE.

**Decisions requested from the coordinator**

1. The nested-reference 404 carries `fields["items.<i>.productId"]` — the only 404 with field detail.
   Keep it (and document it in T10's OpenAPI), or drop the fields and rely on the message?
2. `409 INVOICE_NOT_EDITABLE` for non-draft item edits: confirm before T07 builds on it.
3. Item ids are not stable across a replacement (`deleteMany` + `createMany`), so T09 must key rows
   on `productId`/`position`. Accept as contract, or switch to an upsert-style merge?
4. `readEnv(process.env)` runs on every create, so an invalid `DATABASE_URL`/`BETTER_AUTH_SECRET`
   also produces the sanitized 500. Accept, or read only `TAX_RATE_BPS`?
5. The plan lists `transitionInvoice`/`assertTransition` in this service file while T06 omits them:
   confirm the split so T07 can add them.

**Coverage gaps (additive tests; no code change proposed)**

6. `PUT /api/invoices/<well-formed-unknown-uuid>/items` is not pinned directly (only the
   foreign-owner 404 is); retry-exhaustion `TRANSACTION_CONFLICT` is not exercised for invoices;
   there is no `status` filter + pagination case; `updatedAt` semantics are never asserted.
7. `createInvoiceFixture` calls `calculateTotals` from the module under test to build fixture totals
   — V2's own numbers are hand-computed, so only fixture validity is at stake.

**Awareness**

8. The version-guarded `updateMany` runs before `deleteMany`/`createMany` (correct inside one
   transaction; flagged so the lock order on one invoice row plus its items is conscious).
9. `findMany` + `count` are outside a transaction, so `total` can differ from `data` by one under a
   concurrent write — inherited from T05 and disclosed.
10. An `invoiceNumber` collision would be a sanitized 500 rather than a 409; the number embeds a
    fresh UUID, so it is effectively unreachable.
11. `snapshotItems`' "stock is validated for every line" holds because a retained line must still
    resolve to an active owned product — worth stating explicitly when T07 reuses the helper.

### Recap

T06 adds four invoice *draft* endpoints behind auth and exact-Origin checks, computes all money
server-side in integer cents with a single half-up tax step, snapshots product name/price onto lines
(retaining old snapshots on edit), validates stock without reserving it, and replaces a draft's line
set atomically under a version guard. Its correctness claims rest on 28 real-PostgreSQL tests that
include exact totals, rollback on an invalid line, and a concurrent-edit race. Scope stops at drafts
so T07 can own status transitions and stock effects in the same service file, and the open questions
above should be answered before acceptance.

## 1. Summary

T05 adds the four owner-scoped product endpoints the rest of StockFlow builds on: list with
search and paging, create, read one, update, and soft delete. It introduces one service module
and two Next.js route files, plus 19 integration tests that drive the exported route handlers
against a real database.

## 2. Requirements and scope

In plain terms:

- **I1** — CRUD over products that belong to the signed-in user.
- **I2** — case-insensitive search on name/SKU, paginated with stable ordering and correct counts.
- **I3** — input validation with field-level errors, and duplicate SKU detection on the normalized value.
- **I4** — delete is a soft delete that keeps invoice references intact and keeps the SKU reserved.
- **A6** — authentication is required and enforced before anything else is parsed.
- **A7** — ownership: another user's product is unreachable by any means, including guessing a UUID.
- **N6** — non-functional consistency: uniform JSON errors, `no-store`, `nodejs` runtime, exact
  integers, concurrency handling.

Deliberately out of scope: no product UI (T08); no invoice endpoints and no issue/cancel semantics
for deleted products (T06/T07); no shared-file edits; no hard delete and no restore endpoint.

## 3. Architecture and mental model

StockFlow's layering is route handler → service → Prisma, and T05 slots into it the same way T03 did
for auth:

```
HTTP Request
   ├─ app/api/products/route.ts        GET list · POST create
   └─ app/api/products/[id]/route.ts   GET one · PATCH · DELETE
           order of operations:  requireAuth → assertSameOrigin (mutations) → validate → service
           every handler is wrapped in handleRoute(), which converts thrown errors to JSON
                    ▼
   lib/services/products.ts   all ownership filters and SQL
           reads: getPrisma().product.*     writes: withSerializableRetry(tx => …)
                    ▼
   PostgreSQL  Product: @@unique([userId, sku]), @@index([userId, deletedAt, createdAt])
```

Three boundaries matter:

1. **`handleRoute` is the single error funnel** (`lib/http.ts:54-56`). Handlers never build error
   responses; they throw `AppError`, a `ZodError` or a Prisma error, and `errorResponse`
   (`lib/http.ts:45-51`) maps them to `{ error: { code, message, fields? } }` with
   `cache-control: no-store`. That is why tests can assert exact error bodies.
2. **Ownership is a service concern, not a route concern.** `userId` is always passed down and is
   always part of the `WHERE` clause, so a route cannot forget to scope a query.
3. **Writes are version-guarded inside a serializable transaction** via T01's
   `withSerializableRetry` (`lib/services/transaction.ts:5-16`): `Serializable` isolation, retry on
   `P2034` up to 3 attempts, otherwise rethrow. Product writes reuse it instead of inventing a new
   concurrency story.

## 4. Implementation walkthrough

### 4.1 `lib/services/products.ts` (132 lines)

**Row projection (lines 10-20, 30-40).** `ProductRow` lists exactly the columns allowed to leave
the service; `toProductDto` converts `Date` → ISO string. `userId` and `deletedAt` are absent by
construction, so they cannot leak through a spread. The suite asserts the exact key set
(`tests/integration/products.test.ts:151`).

**The ownership predicate (lines 22-28).**

```ts
const activeRow = (userId: string, id: string) => ({ id, userId, deletedAt: null }) as const;
```

One helper encodes "exists, is mine, is not deleted" and is reused by read, update and delete. This
is the heart of A7 and I4: because `deletedAt: null` is part of the predicate, a soft-deleted row is
indistinguishable from a nonexistent one — same 404, same body.

**`listProducts` (lines 52-74).** One `where` is used twice, built from the escaped search term:

```ts
const search = escapeLikePattern(query.search);
const where = { userId, deletedAt: null, ...(search ? { OR: [
  { name: { contains: search, mode: "insensitive" } },
  { sku:  { contains: search, mode: "insensitive" } }] } : {}) };
```

`mode: "insensitive"` is Prisma's `ILIKE`, so case-insensitivity is a database behaviour rather
than a JS filter. `escapeLikePattern` (lines 46-50) escapes `\`, `%` and `_`, because `contains`
compiles to an `ILIKE` pattern in which those characters would otherwise stay wildcards — the
reviewer-found bug fixed at `51ff472` (see sections 7 and 8). `findMany` (ordered/skipped/taken) and
`count` run concurrently via `Promise.all`; `totalPages` is `total === 0 ? 0 : Math.ceil(total / pageSize)`.
Ordering is `[{ createdAt: "desc" }, { id: "asc" }]` — the `id` tiebreaker keeps same-millisecond rows
from paging non-deterministically, and the suite recomputes the expected order from the returned data
(line 223).

**`getProduct` (lines 77-81).** `findFirst(activeRow)` then `notFound()`, so a foreign, unknown or
deleted id never produces a distinguishable response.

**`createProduct` (lines 83-101).** The insert is plain; the `catch` is the point:

```ts
if (isSkuCollision(error)) throw skuConflict();   // P2002 → 409 DUPLICATE_SKU, fields.sku
```

with `isSkuCollision` (lines 43-44) checking `PrismaClientKnownRequestError && code === "P2002"`.
There is no racy select-then-insert pre-check: the unique index arbitrates, so two simultaneous
creates of one SKU cannot both win. Because the index is `@@unique([userId, sku])` on the raw
column, the same SKU is legal for two different users (test lines 126-141) while a soft-deleted row
still reserves it (the index ignores `deletedAt`).

**`updateProduct` (lines 103-121).** The subtlest function:

```ts
const { version, ...changes } = input;
const data = { version: { increment: 1 } };              // the version bumps itself
for (const [field, value] of Object.entries(changes))
  if (value !== undefined) data[field] = value;          // only fields that were sent

return await withSerializableRetry(async (tx) => {
  if (!(await tx.product.findFirst({ where: activeRow(userId, id), select: { id: true } }))) throw notFound();
  const { count } = await tx.product.updateMany({ where: { ...activeRow(userId, id), version }, data });
  if (count === 0) throw versionConflict();
  return toProductDto(await tx.product.findUniqueOrThrow({ where: { id } }));
});
```

Why not the obvious `update({ where: { id }, data })`?

- **Existence first** separates two failures that would otherwise collapse: unowned/absent/deleted →
  **404** (information hiding), live row with the wrong version → **409**. A lone conditional
  `updateMany` would report "0 rows" for both.
- **`updateMany` with `version` inside the `WHERE`** makes the check part of the statement — a
  compare-and-swap. Under `Serializable`, a concurrent writer either trips `P2034` (retried by the
  helper) or finds the version already incremented (→ 409). Exactly one writer wins.
- **The empty-update case is rejected upstream**: `updateProductSchema`
  (`lib/validation/schemas.ts:16`) requires at least one mutable field besides `version`, producing
  a 422 keyed `_root`.
- **The `data` loop** copies only present keys, so omitted fields stay untouched while an explicit
  `description: null` clears the column (both covered by the PATCH at line 163).

**`deleteProduct` (lines 123-131).** Same existence/version discipline; the mutation is
`{ deletedAt: new Date(), version: { increment: 1 } }`. Two consequences: deletion is an `UPDATE`,
so no foreign key ever fires (relevant because `InvoiceItem.product` is `onDelete: Restrict`,
`prisma/schema.prisma:127`); and the version still advances, so a stale client can neither re-delete
nor resurrect the row.

### 4.2 `app/api/products/route.ts` (38 lines)

```ts
export const runtime = "nodejs";                       // Prisma needs Node, not the Edge runtime
const pageResponse = (result) => Response.json(result, { status: 200, headers: { "cache-control": "no-store" } });

export function GET(request: Request): Promise<Response> {
  return handleRoute(async () => {
    const user = await requireAuth(request.headers);          // 1. auth
    const query = readQuery(request, productListSchema);      // 2. validate
    return pageResponse(await listProducts(user.id, query));  // 3. service
  });
}
```

- **`pageResponse`, not `dataResponse`.** `dataResponse` wraps in `{ data }` (`lib/http.ts:11-13`),
  which would nest a page as `{ data: { data, pagination } }`. List endpoints return the plan's
  `Page` envelope directly. T10's OpenAPI spec must match this.
- **`readQuery` (lines 15-19)** parses `URL.searchParams` into an object and runs it through the
  same **strict** schema family as bodies, rethrowing the `ZodError` that `handleRoute` maps to 422.
  That is why `?sort=name` is a 422 with `fields.sort` instead of a silently ignored parameter.

`POST` runs auth → `assertSameOrigin` → `readJson` → service → `dataResponse(..., 201)`. The origin
check sits *after* authentication (so an anonymous bad-Origin request is 401, not 403) and *before*
parsing (so a foreign-origin request with a malformed body is still 403).

### 4.3 `app/api/products/[id]/route.ts` (48 lines)

`parseId` (lines 11-17) validates **and** normalizes the path segment:

```ts
const result = domainIdSchema.safeParse(raw);            // z.uuid().transform(id => id.toLowerCase())
if (!result.success) throw new AppError(422, "VALIDATION_ERROR", "Invalid input",
  { id: result.error.issues.map((issue) => issue.message) });
```

This is the contract decision reviewers should notice: a non-UUID segment is **422 `VALIDATION_ERROR`**
(treating it as malformed input), while a well-formed UUID that is unknown or not yours is 404.

All three handlers `await context.params` because this repository's Next 16 route context is a
**Promise** — `AGENTS.md` warns that this is not the Next the model may remember, and it was the
first TypeScript error the implementation hit, which is why the red-stage skeleton mirrored that
signature.

`DELETE` returns `new Response(null, { status: 204, headers: { "cache-control": "no-store" } })`.

### 4.4 End-to-end happy path

A user with a session cookie creates, renames, then deletes a product:

1. `POST /api/products`, `Origin: http://localhost:3100`, body
   `{"sku":" abc-1 ","name":" Widget ","unitPrice":1299,"quantityOnHand":10}`.
   `requireAuth` resolves the session; `assertSameOrigin` matches the origin exactly; `readJson`
   checks the content type, parses, and `createProductSchema` normalizes → `sku` `ABC-1`,
   `name` `Widget`. Insert with `userId`, `description: null`, `version: 0`.
   Response `201 {"data":{"id":…,"sku":"ABC-1","name":"Widget","description":null,"unitPrice":1299,
   "quantityOnHand":10,"version":0,"createdAt":"2026-…Z","updatedAt":"2026-…Z"}}`, `no-store`.
2. `PATCH /api/products/<id>` `{"version":0,"quantityOnHand":4}` → existence check passes, the
   conditional update matches `version = 0`, writes the new stock and `version: 1` → `200`.
3. `DELETE /api/products/<id>` `{"version":1}` → sets `deletedAt`, `version = 2` → `204`, empty body.
4. Any later `GET /api/products/<id>` → `404 {"error":{"code":"NOT_FOUND","message":"Product not found"}}`;
   the row remains, its SKU stays reserved, and referencing invoice items are untouched.

Repeating step 2 with the stale `version: 0` returns `409 VERSION_CONFLICT` and leaves the row intact
(test line 376).

## 5. Correctness, edge cases and security

**Authentication ordering (A6).** Every handler's first statement is `requireAuth(request.headers)`,
which throws `AppError(401, "UNAUTHORIZED", …)` (`lib/auth/session.ts:16-20`) before any URL or body
parsing. The suite proves it with deliberately broken input (lines 53-66): list with
`?page=0&bogus=1`, create with `{not json`, read/patch/delete with `not-a-uuid` — all five must be
401 with identical bodies and `no-store`, so a malformed request cannot teach an unauthenticated
caller anything. Lines 68-72 add a forged cookie name.

**Ownership (A7).** A row is reachable only through `activeRow(userId, id)`, so "someone else's id",
"a random UUID" and "a soft-deleted id" produce byte-identical 404s. Tests 103-124 assert the triple
404 *and* that the owner still sees the row, with `name`/`version`/`deletedAt` untouched — a failed
attack must not partially write. Tests 126-141 verify the mirror image: the same normalized SKU for
two users yields two rows, and each user's search returns only their own.

**Cross-site request forgery (N6).** Mutations call `assertSameOrigin` (`lib/http.ts:27-34`), which
compares the `Origin` header to `BETTER_AUTH_URL` by exact string. Tests 76-99 cover a foreign
origin on create/patch/delete (403 `ORIGIN_REJECTED`) plus a request with no `Origin` at all, then
assert the database still holds the original values and exactly one row. Two residual points are
recorded in section 8: reads are not origin-checked, and a missing or malformed `BETTER_AUTH_URL`
yields `500 CONFIGURATION_ERROR` (fail-closed, but it looks like a server fault).

**Validation (I3).** `readJson`/`readQuery` throw the raw `ZodError`; `errorResponse`
(`lib/http.ts:36-42`) converts it into 422 with a `fields` map keyed by dotted path, using `_root`
for pathless issues and expanding `unrecognized_keys` per key. That is what makes strict-object
rejection of `userId`, `version` and `deletedAt` readable as `fields.userId` rather than a generic
error. Tests 261-288 (create, 15 cases), 290-305 (query, 6 cases) and 307-336 (patch/delete,
12 cases) assert `fields.<key>` exists, pinning *where* the error is reported, not merely that one
occurred. Security value: a client cannot inject `userId` to plant a product in another workspace,
nor smuggle `deletedAt` to fake a deletion.

**Money and stock precision (N6).** `unitPrice` and `quantityOnHand` come from
`integer(0, 2147483647)` and `integer(0, 1000000)` (`lib/validation/schemas.ts:3,14`):
`z.number().int()` rejects `10.5`, `min(0)` rejects negatives, `max` rejects `2147483648` and
`1000001`. Prices are integer cents, so this layer cannot introduce float rounding; the single
half-up tax step lives in T02's `lib/money.ts` and is untouched here. `version` is bounded too.

**Concurrency (N6).** Two writers are handled by composable layers: `withSerializableRetry` retries
genuine serialization failures (`P2034`, ≤3 attempts), and the conditional `updateMany` turns a lost
race into 409 `VERSION_CONFLICT`. A *leaked* `P2034` is additionally mapped to 409
`TRANSACTION_CONFLICT` (`lib/http.ts:49`), so retry exhaustion is still a clean client error. Tests
387-398 fire two simultaneous same-version PATCHes and require exactly one 200 plus one 409 with
stored `version = 1`; this is only meaningful against real PostgreSQL, which is how it runs.

**Deletion semantics (I4).** Tests 401-446 assert three properties: an invoice item created directly
through Prisma keeps its `productId`, `productName`, `unitPrice` and `quantity` after the product is
soft-deleted (snapshots survive by construction, since the row is never removed and `Restrict` never
fires); the product disappears from reads; and recreating SKU `ref-keep` is a 409 because the unique
index ignores `deletedAt`. Lines 435-445 close the loop by PATCHing the deleted row and requiring
404 — no restore path, no zombie rows.

**Cleanup.** The test file disconnects Prisma in `afterAll` and relies on the T00 harness for
isolation: `tests/setup.ts` resets the database in `beforeEach` for integration files and fails
closed unless `STOCKFLOW_TEST_DATABASE_READY=1`, `TEST_DATABASE_URL` is set, and `DATABASE_URL`
equals `TEST_DATABASE_URL`. `fileParallelism: false` makes the suite serial, which is what makes the
exact global row-count assertions valid.

**Not applicable here:** money rounding and tax math (T02), session issuance and revocation (T03),
invoice numbering and status transitions (T06/T07), UI authorization (T08/T09).

## 8. Findings, limitations and open decisions

**F1 — found in review, fixed at `51ff472`.** `listProducts` built
`{ name: { contains: search, mode: "insensitive" } }`, which Prisma renders as an `ILIKE` with the
value as a *bound parameter*. That parameterized the input, so it was **not** SQL injection and had no
data-integrity or authorization impact; but `%` and `_` kept their wildcard meaning inside the
pattern, so searching `%` returned every product instead of only rows that contain one, and `AB_1`
would also have matched `ABX1` — a deviation from the literal substring search the card documents.
The coordinator chose to fix it rather than accept it: `escapeLikePattern`

**Risks and notes.**
- **N1 — SKU normalization is application-level.** `trim().toUpperCase()` lives in the Zod schema
  (`lib/validation/schemas.ts:14`) while the unique index is on the raw column, so a writer that
  bypasses the schema can create a lowercase row that will not collide with an uppercase one. Seed
  data is uppercase (`prisma/seed.ts:22-26`) and fixtures use uppercase. T06/T07 should reuse the
  schema (or normalize) when they touch SKUs.
- **N2 — `findMany` and `count` are two statements outside a transaction**
  (`lib/services/products.ts:61-69`), so a concurrent insert or delete can make `total` disagree with
  `data` by one. The plan requires stable ordering, not snapshot isolation; flagged so it is a
  decision rather than an accident.
- **N3 — exact-origin matching is brittle.** `assertSameOrigin` requires byte equality with
  `BETTER_AUTH_URL` including host string and port; a mismatch is 403, and a missing/invalid variable
  is 500 `CONFIGURATION_ERROR`. Consistent with T03's recorded caveat; it will bite anyone opening the
  app on `127.0.0.1` while the env says `localhost`.
- **N4 — reads are not origin-checked** and no explicit `sameSite` was found in
  `lib/auth/server.ts:30-33`, so cross-site read protection rests on the library default. Inference,
  not verified — worth confirming in T04/T10.
- **D1 — card wording.** The card's Validation section asks for a "manual version stale-write test";
  the shipped evidence is automated (stale PATCH 409 plus a concurrent-writer test) and the card
  discloses that substitution. Not a defect.

### Recap

> T05 exposes five product operations through two route files. Each handler authenticates first,
> then (for writes) checks that the request origin equals `BETTER_AUTH_URL`, then validates with the
> shared strict Zod schemas, which trim and uppercase the SKU so duplicates are caught on the
> normalized value even though the database index is on the raw column. All real logic lives in
> `lib/services/products.ts`, where every query includes `userId` and `deletedAt: null`, so another
> user's product and a deleted product are both a plain 404. Updates and deletes are
> compare-and-swaps inside a serializable transaction: the client sends the `version` it last saw,
> the `WHERE` clause matches on it, and a loser receives 409 instead of silently overwriting. Delete
> is an `UPDATE` of `deletedAt`, which is why invoice-item snapshots survive, why the SKU stays
> reserved, and why there is no restore path. Errors flow through one funnel
> (`handleRoute` → `errorResponse`), so every response is `{ error: { code, message, fields? } }`
> with `no-store`. Nineteen integration tests against real PostgreSQL pin all of that, and a reviewer
> re-run reproduced 75/75 plus 67/67 unit, clean lint/typecheck/build, with one search-wildcard
> deviation found by adversarial probing — fixed before merge under `51ff472`, which escaped the LIKE
> metacharacters and lifted the suite to 25 product cases (81/81 integration).

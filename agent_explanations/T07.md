## 1. Summary

Before T07 an invoice could be created and its draft lines edited, but it could never leave `DRAFT`:
there was no way to issue it, mark it paid, or cancel it, and no code touched product stock. T07 adds
the missing half of the invoice lifecycle:

- `PATCH /api/invoices/[id]/status` accepts `{ version, status }` and moves an invoice along the only
  legal edges: `DRAFT → ISSUED`, `DRAFT → CANCELLED`, `ISSUED → PAID`, `ISSUED → CANCELLED`.
- Issuing makes the invoice real: it re-checks live stock, then deducts **every** line exactly once.
  Cancelling an *issued* invoice puts that stock back exactly once. Cancelling a *draft* moves no stock,
  and `PAID`/`CANCELLED` are terminal — repeating an action is a 409, never a second effect.
- All of it happens in one serializable transaction: the status change and the stock movement either both
  commit or both roll back, and every product row that moves gets its `version` incremented so a stale
  manual stock edit cannot silently overwrite the deduction.

The mental model to hold onto: **the invoice row is the claim, and the product rows are the ledger.** A
transition is claimed with a conditional `UPDATE ... WHERE status = <old> AND version = <n>`; only the
winner of that claim may touch products, and the product updates are themselves conditional
(`quantityOnHand >= qty` when issuing, `quantityOnHand <= 1000000 - qty` when restoring).

## 3. Architecture and mental model

StockFlow is a Next.js App Router application, so every API endpoint is a **Route Handler**: a module
that exports HTTP methods and receives a standard `Request`. T07 adds one such module and extends one
service. The layering in this codebase (established by T02–T06) is:

```
client (later: T09 React form)
        │  PATCH { version, status }
        ▼
app/api/invoices/[id]/status/route.ts   ← HTTP concerns: auth, Origin, path id, body schema, status codes
        │  transitionInvoice(userId, id, input)
        ▼
lib/services/invoices.ts                ← business rules: legal transitions, ownership, version guard, stock
        │  tx.product.updateMany / tx.invoice.updateMany
        ▼
PostgreSQL (Prisma 7 + serializable transactions from lib/services/transaction.ts)
```

| Component | Responsibility | Owner |
|---|---|---|
| `app/api/invoices/[id]/status/route.ts` (new, 28 lines) | Authenticate, enforce same-origin, validate the UUID path id and the strict `{version,status}` body, call the service, serialise the DTO, map errors | T07 |
| `lib/services/invoices.ts` → `transitionInvoice` (new, lines 299–318) | The whole lifecycle rule set: existence, legal edge, version claim, stock deduct/restore, DTO | T07 (file handed over by T06) |
| `assertTransition` + `LEGAL_TRANSITIONS` (new, lines 215–247) | The state machine as data | T07 |
| `deductStock`, `restoreStock`, `sortByProduct` (new, private, lines 238–291) | Conditional, ordered product writes | T07 |
| `withSerializableRetry` (`lib/services/transaction.ts`) | Runs the callback in a `Serializable` transaction, retrying only Prisma `P2034` (serialization failure), three attempts total | T01 — read-only for T07 |
| `requireAuth`, `assertSameOrigin`, `readJson`, `dataResponse`, `handleRoute`, `AppError` (`lib/http.ts`, `lib/auth/session.ts`) | Auth lookup, exact-Origin check, strict JSON parsing, `{data}` envelope with `no-store`, error→HTTP mapping | T02/T03 — read-only |
| `transitionInvoiceSchema` (`lib/validation/schemas.ts`) | Strict Zod object: `version >= 0`, `status ∈ ISSUED | PAID | CANCELLED`, unknown keys rejected | T02 — read-only |
| `Invoice` / `InvoiceItem` / `Product` and their CHECK constraints | The durable facts: `status`, `version`, `quantityOnHand`, and the `quantityOnHand BETWEEN 0 AND 1000000` bound | T01 migration — read-only |

Why this shape: T06 had already built the invoice service with exactly this pattern — parse in the route,
decide in the service, claim with a version-guarded `updateMany`, write inside `withSerializableRetry`.
T07 copies the pattern instead of inventing a second one, so a reviewer can read `replaceInvoiceItems`
(lines 189–212) and `transitionInvoice` (lines 299–318) side by side.

### 4.1 The state machine as data (`lib/services/invoices.ts:215–247`)

```ts
const LEGAL_TRANSITIONS: Record<InvoiceStatus, readonly InvoiceStatus[]> = {
  DRAFT: ["ISSUED", "CANCELLED"],
  ISSUED: ["PAID", "CANCELLED"],
  PAID: [],
  CANCELLED: [],
};

export function assertTransition(from: InvoiceStatus, to: InvoiceStatus): void {
  if (!LEGAL_TRANSITIONS[from].includes(to)) throw transitionConflict(from, to);
}
```

`InvoiceStatus` is the union `"DRAFT" | "ISSUED" | "PAID" | "CANCELLED"`, so the record is exhaustive by
type: adding a fifth status would break typecheck until the table is extended. Encoding the graph as data
(rather than separate `if` statements) makes "PAID and CANCELLED are terminal" visibly just `[]`, and it is
the same table the test matrix enumerates: 4 legal + 8 illegal pairs = 12 = every `from`×`to` combination
(the three same-status repeats included; `status: "DRAFT"` is not even accepted as a body value, so
`DRAFT → DRAFT` is impossible by schema rather than by rule).

The error mapping is a deliberate, ratified contract:

- **409, not 404**: the invoice exists and the caller may see it; only its *state* forbids the action, so
  this is a conflict rather than a missing resource.
- **409, not 422**: the request is well-formed — `CANCELLED` is a legal status value, it simply is not
  reachable from `PAID`.
- **Code `INVOICE_NOT_EDITABLE` with a transition-specific message** (coordinator ruling of 2026-09-18 on
  T06 item 5, since T06 had left the exact wording to T07). T06 had established that code for "the state
  forbids this operation" (item edits on a non-draft invoice). The coordinator ruled that T07 keeps the
  code but replaces the wording, because T09 renders messages to users and "Only draft invoices can have
  their items replaced" would be nonsense for a *Cancel* click. The message is generated from the actual
  pair — `Invoice status cannot change from PAID to CANCELLED` — so a log or a UI banner is
  self-explanatory.
- **Repeats are conflicts, not idempotent successes**: the plan states "Repeating a status action returns
  409, without repeating stock effects", so a second *Issue* on an issued invoice is a 409. That is also
  what makes the concurrency story simple: there is never a "nothing to do, but 200" branch.

### 4.2 Issuing: `deductStock` (`lib/services/invoices.ts:254–270`)

```ts
async function deductStock(tx, userId, items) {
  for (const item of sortByProduct(items)) {
    const { count } = await tx.product.updateMany({
      where: { id: item.productId, userId, deletedAt: null, quantityOnHand: { gte: item.quantity } },
      data: { quantityOnHand: { decrement: item.quantity }, version: { increment: 1 } },
    });
    if (count === 0) {
      const product = await tx.product.findFirst({ where: { id: item.productId, userId },
        select: { name: true, quantityOnHand: true, deletedAt: true } });
      if (!product || product.deletedAt) throw productNotFound(item.position);
      throw insufficientStock(item.position, product.quantityOnHand, product.name);
    }
  }
}
```

Five decisions worth explaining:

1. **The guarded `updateMany` *is* the stock check.** Read-then-write would leave a window in which two
   concurrent issues both see enough stock and both decrement — the "oversell" bug this company exists to
   stop. Here PostgreSQL evaluates `quantityOnHand >= item.quantity` atomically with the write, so the
   second transaction matches zero rows and cannot damage anything. This is V5: availability is validated
   when a line is added (T06) and *authoritatively re-checked* when the invoice becomes real.
2. **`deletedAt: null` in the guard** implements the I4 half that says a soft-deleted product cannot be
   issued, even when its stock would still cover the line.
3. **The failure branch exists only to explain itself.** `count === 0` means "the guard failed"; a re-read
   (deliberately without a `deletedAt` filter) distinguishes *deleted product* → 404 `NOT_FOUND` naming the
   line (`fields["items.<position>.productId"]`), consistent with T06's rule that deleted/foreign/unknown
   product references are 404 and actionable in the UI ("remove or replace this line"), from *insufficient
   stock* → 409 `INSUFFICIENT_STOCK` with `fields["items.<position>.quantity"]` and a message naming the
   product and its current quantity, matching T06's create/edit conflict wording.
4. **Ordered writes** (`sortByProduct`, lines 238–239; it sorts a copy, so the caller's array is not
   mutated): two concurrent issues touching the same pair of products try to lock them in the same order,
   which is what prevents deadlock cycles. The key is the product UUID — arbitrary but total and stable.
5. **`version: { increment: 1 }` on every stock write.** This is the half of V9 that T07 owns: a manual
   stock edit that was composed before the issue carries the old version, so its own guarded update matches
   nothing and is rejected with 409 `VERSION_CONFLICT` instead of silently resurrecting deducted stock.

Because the loop throws on the first failure, a two-line issue whose second line fails leaves the first
line's deduction to the transaction rollback — that is V6's atomicity claim, and the transaction is the
serializable one supplied by `withSerializableRetry`.

### 4.3 Cancelling: `restoreStock` (`lib/services/invoices.ts:277–291`)

```ts
async function restoreStock(tx, userId, items) {
  for (const item of sortByProduct(items)) {
    const { count } = await tx.product.updateMany({
      where: { id: item.productId, userId, quantityOnHand: { lte: MAX_STOCK - item.quantity } },
      data: { quantityOnHand: { increment: item.quantity }, version: { increment: 1 } },
    });
    if (count === 0) {
      const product = await tx.product.findUniqueOrThrow({ where: { id: item.productId },
        select: { name: true, quantityOnHand: true } });
      throw stockOverflow(product.name, product.quantityOnHand);
    }
  }
}
```

The three deliberate differences from `deductStock`:

1. **No `deletedAt: null` filter.** I4 requires that cancelling an issued invoice returns the stock of a
   product that was deleted *after* the issue; the row still exists (deletion is soft and the FK is
   `RESTRICT`), so the restore simply must not care about `deletedAt`.
2. **The guard is an upper bound, not a lower one.** `MAX_STOCK = 1_000_000` (line 223) mirrors the
   migration's `Product_quantityOnHand_check`. Without this guard, restoring a line into a product whose
   stock was raised to the maximum in the meantime would violate the database CHECK and surface as a
   sanitized 500. With it, the database refuses the write, `count` is 0, and the service reports a
   meaningful 409 — which is exactly what the plan means by "cancellation overflow rolls back with 409".
3. **A new code, `STOCK_OVERFLOW`, with a message and no `fields`.** The plan names no code for this case,
   and no request field can fix it (the manual stock write has to be lowered first), so a field map would
   be noise. This is the only brand-new error code T07 introduces, which is why §7 asks the coordinator to
   ratify it and T10 to document it.

`findUniqueOrThrow` in the failure branch is unreachable in practice: `InvoiceItem.productId` is
`RESTRICT`-protected, so a referenced product row cannot disappear. It is the cheapest way to produce an
honest error if the invariant is ever broken, rather than adding another branch nobody can test.

### 4.4 The orchestrator: `transitionInvoice` (`lib/services/invoices.ts:299–318`)

```ts
export async function transitionInvoice(userId, id, input): Promise<InvoiceDetailDto> {
  return withSerializableRetry(async (tx) => {
    const invoice = await tx.invoice.findFirst({ where: { id, userId }, include: ITEMS_ASCENDING });
    if (!invoice) throw notFound();
    assertTransition(invoice.status, input.status);
    if (invoice.version !== input.version) throw versionConflict();

    const { count } = await tx.invoice.updateMany({
      where: { id, userId, status: invoice.status, version: input.version },
      data: { status: input.status, version: { increment: 1 } },
    });
    if (count === 0) throw versionConflict();

    if (invoice.status === "DRAFT" && input.status === "ISSUED") await deductStock(tx, userId, invoice.items);
    if (invoice.status === "ISSUED" && input.status === "CANCELLED") await restoreStock(tx, userId, invoice.items);

    const updated = await tx.invoice.findUniqueOrThrow({ where: { id }, include: ITEMS_ASCENDING });
    return toDetailDto(updated);
  });
}
```

Read it as four phases: **resolve → decide → claim → act**.

- **Resolve** fetches the invoice *scoped by `userId`*, which is how A7 is enforced: another user's id is
  indistinguishable from an unknown one and answers 404 `NOT_FOUND`. The fetch is a plain read — it takes
  no lock, which is fine because it is never the thing that authorises the write.
- **Decide** applies the two rules that need the current row: is this edge legal (`assertTransition`), and
  is the caller's `version` current. The order matters and is deliberate: **state before version**, so an
  illegal *Cancel* on a `PAID` invoice answers the state conflict even if the version is also stale, which
  is the more useful message. The same ordering exists in T06's `replaceInvoiceItems`, so the two paths
  behave alike.
- **Claim** is the conditional `updateMany` on `status + version`. This is the race-safe step: two
  concurrent transitions of the same invoice can both read `DRAFT`/`version 0`, but only one `UPDATE`
  matches; the loser's `count` is 0 and it answers 409 `VERSION_CONFLICT`. Under `Serializable`, the loser
  may instead be aborted by PostgreSQL with a `P2034` serialization failure, which
  `withSerializableRetry` retries (up to three attempts) — on the retry it sees the winner's row and fails
  the claim or the edge check properly.
- **Act** applies the stock effect for exactly two edges (`DRAFT→ISSUED`, `ISSUED→CANCELLED`) and nothing
  for `DRAFT→CANCELLED` or `ISSUED→PAID`. Because the claim already succeeded inside this transaction, a
  throw here rolls the claim back too — that is the mechanism behind "a failed late line leaves no
  status change and no partial deduction".

A subtle point worth stating because it looks wrong at first glance: the items used for the stock effect
were read *before* the claim. Could a concurrent draft edit have swapped them in between? No — an edit
bumps `version`, so any edit that committed between the read and the claim makes the claim miss, which
aborts this attempt. The lines deducted are therefore always the lines of the claimed version. The
`edit racing an issue` test in §6 pins exactly that reasoning.

Finally the row is re-read (with `ITEMS_ASCENDING`, lines 301/315, so items come back ordered by
`position`) and mapped through the shared `toDetailDto`, so the response is byte-compatible with
`GET /api/invoices/[id]`. T09 can therefore replace its invoice state with the response without a second
request.

### 4.5 The route (`app/api/invoices/[id]/status/route.ts`, 28 lines)

```ts
export const runtime = "nodejs";
export type InvoiceStatusRouteContext = { params: Promise<{ id: string }> };

function parseId(raw: string): string { /* domainIdSchema.safeParse -> 422 with fields.id */ }

export async function PATCH(request: Request, context: InvoiceStatusRouteContext): Promise<Response> {
  return handleRoute(async () => {
    const user = await requireAuth(request.headers);
    assertSameOrigin(request);
    const id = parseId((await context.params).id);
    const input = await readJson(request, transitionInvoiceSchema);
    return dataResponse(await transitionInvoice(user.id, id, input));
  });
}
```

Line-by-line rationale:

- `runtime = "nodejs"`: the handler reaches Prisma/the `pg` driver through the service, which cannot run
  on the Edge runtime. Every data route in this project declares the same thing.
- `handleRoute` wraps everything so any thrown `AppError` or `ZodError` becomes the project's standard
  `{ error: { code, message, fields? } }` body (via `errorResponse`) instead of an unhandled rejection.
  Non-`AppError` throwables are deliberately sanitized to a 500 `INTERNAL_ERROR`, which is how N6's
  "sanitized unexpected failure" rule is respected without leaking Prisma internals.
- **Order is a contract, not a style choice.** `requireAuth` runs *before* anything is parsed, so an
  anonymous request with a garbage body or a malformed id still answers 401 (A6). Only then does
  `assertSameOrigin` run (403 for a missing/foreign Origin — a CSRF guard for cookie-authenticated
  mutations), then `parseId` (422 `fields.id` with the Zod message), then the strict body schema
  (422 `fields.version`/`fields.status`, or `fields.userId` etc. for smuggled keys). A malformed id
  therefore beats a malformed body, and a 400 `INVALID_JSON` only happens for an authenticated,
  same-origin, well-formed-id request.
- `context.params` is `await`ed: in this Next version dynamic route params are asynchronous, so
  `context.params` is a promise.
- `dataResponse(dto)` is the shared `{ data: ... }` envelope with `cache-control: no-store`, which is the
  same shape GET returns.
- **There is deliberately no `GET` on this module.** A "status" is not a resource; reading the invoice is
  `GET /api/invoices/[id]`, owned by T06. Adding a redundant GET here would create a second source of
  truth for the same DTO.

### 4.6 One happy path, end to end, with numbers

Setup: owner registers, owns **A** (`unitPrice 1299`, `quantityOnHand 10`, `version 0`) and **B**
(`unitPrice 999`, `quantityOnHand 4`, `version 0`). (Illustrative inputs; the suite uses the same shapes
with different fixture data.) Say A sorts before B by UUID, as the implementation does.

1. `POST /api/invoices` with `{customerName, issueDate, dueDate, items: [{A, 3}, {B, 4}]}` → **201**, T06
   code path: snapshots `A@1299`, `B@999`, `subtotal 3897 + 3996 = 7893`, `taxAmount 868` (11 % of 7893 =
   868.23, half-up), `total 8761`, `status DRAFT`, `version 0`, `taxRateBps 1100`, items at positions 0
   and 1. **Stock is untouched** — drafts reserve nothing.
2. `PATCH /api/invoices/<id>/status` with `{version: 0, status: "ISSUED"}`:
   - auth resolves the owner; Origin matches; the id is a UUID; the body passes the strict schema;
   - the transaction reads `DRAFT`, version 0, items `[A:3 @pos0, B:4 @pos1]`;
   - `assertTransition(DRAFT, ISSUED)` passes; `0 === 0` passes;
   - the claim `UPDATE Invoice SET status='ISSUED', version=version+1 WHERE id AND userId AND status='DRAFT' AND version=0`
     affects one row;
   - `deductStock`: A's guarded update (`quantityOnHand >= 3`) affects one row → A becomes `7`, `version 1`;
     B's guard (`>= 4` against stock 4) affects one row → B becomes `0`, `version 1`;
   - the row is re-read and returned → **200** `{data: {status: "ISSUED", version: 1, subtotal: 7893,
     taxAmount: 868, total: 8761, items: [A@1299×3, B@999×4]}}` with `no-store`.
3. `PATCH .../status` with `{version: 1, status: "CANCELLED"}`: claim moves `ISSUED → CANCELLED`, version 2;
   `restoreStock` adds back exactly the same lines → A `10`/`version 2`, B `4`/`version 2`; **200** with
   `status CANCELLED, version 2`.
4. `PATCH .../status` with `{version: 2, status: "PAID"}`: `assertTransition(CANCELLED, PAID)` throws before
   any write → **409** `{code: "INVOICE_NOT_EDITABLE", message: "Invoice status cannot change from
   CANCELLED to PAID"}`. Stock rows and the invoice are byte-identical to step 3's end state.

## 5. Correctness, edge cases and security

**Input validation.** The body schema (`transitionInvoiceSchema`, T02-owned) is a *strict* object: `version`
must be an integer ≥ 0, `status` must be exactly one of `ISSUED | PAID | CANCELLED`. Consequences worth
knowing: `status: "DRAFT"` is a 422 (you cannot un-issue by asking for the status you already have), a
smuggled `userId`/`status`-adjacent key is a 422 with that key in `fields`, and a missing `version` is a
422 rather than a silent "last write wins". The `version` requirement is what makes optimistic concurrency
possible at all: without it the endpoint would have to choose between blind writes and server-side locking.

**Ownership and non-disclosure (A7).** Every query is scoped by `userId` — the invoice fetch and both
product updates. A foreign invoice id is therefore *indistinguishable* from an unknown one (404), so the
endpoint does not confirm that someone else's invoice exists. The `userId` filter on the product writes is
belt-and-braces: invoice lines can only reference products owned by the invoice owner (T06 validated that at
write time and ownership never changes), but leaving the filter in costs nothing.

**CSRF/origin.** The mutation requires the exact `BETTER_AUTH_URL` origin; a browser form post from another
site cannot carry the session cookie and pass the check. This is the same guard the T06 mutation routes use.
A known deployment nuance carried forward from T03/T06: the origin must match the string the app is actually
served on, because the comparison is exact (no trailing slash, no different port).

**Atomicity and concurrency.** Three mechanisms combine:

1. *One transaction* (`Serializable`) around the claim and the stock writes, so a failure anywhere reverts
   everything, including the status change. This is what "late failure rolls back deductions/status" means
   in practice.
2. *A conditional claim* (`status = <old> AND version = <n>`) so exactly one concurrent caller can move a
   given invoice from a given state, and each successful move bumps the version for the next decision.
3. *Conditional, ordered product writes* (`quantityOnHand >= qty` / `<= MAX - qty`, sorted by product id)
   so stock can neither go negative, nor exceed the database bound, nor be double-applied.

The retry helper retries only Prisma `P2034` (serialization failure) up to three attempts and rethrows
anything else; a caller that loses the race therefore sees a 409 (`VERSION_CONFLICT`, `INVOICE_NOT_EDITABLE`
if the retry observes the new state, or `TRANSACTION_CONFLICT` when attempts are exhausted) and never a
half-applied result. Deadlocks (`40P01`) are *not* retried by that helper — ordered writes make them
unlikely, but a deadlock would surface as a sanitized 500. That is listed as a residual risk in §7 rather
than papered over.

**Precision.** T07 performs no money arithmetic at all: it moves `status`/`version` on the invoice and
`quantityOnHand`/`version` on products, and returns the totals T06 computed and stored as integer cents. So
there is no rounding question here, no float, and no path that could silently recompute a historical total
from current prices — the condition the product requirements care most about.

**Rejected-transition hygiene.** Every rejection happens *before* the claim (`404`, state conflict, version
conflict) or is rolled back by the transaction (stock failures), and the success path returns a fresh read
of the committed row. The tests assert the negative space explicitly: after each rejection, the product rows
and the invoice row (status/version/items) are compared field-by-field against a snapshot taken before the
attempt.

**Not applicable here (do not expect T07 to handle it):** rate limiting, multi-currency, tax recalculation,
invoice deletion or metadata editing, partial issuing, restoring soft-deleted products, emails/PDF export,

Two deliberate test-design notes a reviewer should weigh:

- **Race losers are not asserted to one specific code.** A loser can observe `VERSION_CONFLICT`, a retried
  attempt that now sees the new state (`INVOICE_NOT_EDITABLE`), or retry exhaustion
  (`TRANSACTION_CONFLICT`) — all three are 409 and none is a stock effect. The tests pin the *invariants*
  (`[200, 409]`, exact final stock/version, item rows) rather than a code that depends on which transaction
  PostgreSQL happened to abort. The one exception is the oversell race, where the loser's stock is genuinely
  gone, so `INSUFFICIENT_STOCK` is deterministic and is pinned.
- **Fixtures use the shipped routes.** Drafts are created through `POST /api/invoices` (not Prisma), the
  stock reductions/deletes that break a draft go through the product API, and each test registers its own
  users, so nothing depends on cross-test state (the harness still resets the database before every test).
  The file pins `process.env.TAX_RATE_BPS = "1100"` for draft creation, exactly as T06's suite does and as
  the runner already injects, so assertions cannot drift with a developer's local `.env`.

## 7. Findings, limitations and reviewer checkpoints

**No code/card discrepancies were found in this pass.** Every claim in the card that this document spot-checked
matched the pinned revision: the 25 cases exist and are named as described, the diff footprint is four files
(`git diff --stat ae380fd 36f982e`), the tested revision is documentation-free apart from the card, and the
contract notes match the code (state-before-version, transition message, 404 for deleted products at issue,
`STOCK_OVERFLOW` message-only).

Decisions and risks the coordinator should rule on or record before acceptance:

1. **Ratify `409 STOCK_OVERFLOW`** as the cancellation-overflow contract. The plan mandates a 409 there but
   names no code, and T07 introduces this one. It is message-only because no request field can fix it; T10
   needs it in the OpenAPI spec and README error table.
2. **Record the transition-message ruling durably.** The coordinator chose "same code, transition-specific
   message" in this session; the graph/plan/OpenAPI should carry it, since T09 renders the string.
3. **Accept the race-loser tolerance.** Losers may answer `VERSION_CONFLICT`, `INVOICE_NOT_EDITABLE` or
   `TRANSACTION_CONFLICT`. Pinning a single code would require a different mutual-exclusion design (e.g. row
   locks plus a fixed order) for no correctness gain; the invariants are what the tests pin.
4. **Accept 404 for a soft-deleted product line at issue time** (T06 parity) rather than a 409. It is the
   actionable answer for the UI ("replace that line"), and it keeps "deleted product reference = 404"
   consistent across create, edit and issue.
5. **Accept the live product name in the `INSUFFICIENT_STOCK` message.** If a product is renamed after the
   snapshot, the message names the current name while the invoice line shows the snapshot name. T06 behaves
   the same way; changing it would mean a service contract change on a shared helper.
6. **Consider a follow-up task for the `1_000_000` stock bound.** The literal now appears in
   `lib/money.ts`, `lib/validation/schemas.ts` (twice), the initial migration (twice) and
   `lib/services/invoices.ts` (`MAX_STOCK`). A single shared constant owned by T02's schemas module would
   remove the drift risk, but T07 must not edit that file unilaterally — hence the request, not a change.
7. **Deadlocks are not retried** by `withSerializableRetry` (only `P2034`), so a `40P01` would surface as a
   sanitized 500 rather than a 409. Ordered product writes make this unlikely; hardening the T01 helper is
   out of T07's ownership. Worth a note in T10's limitations or a small future task.
8. **`assertTransition` has no direct unit test.** It is a one-line predicate fully exercised through the API
   path (all 12 pairs). Direct unit coverage would be a new commit, so it is offered as a question rather
   than assumed.
9. Informational: `summaryKeys`/`itemKeys` and the "pin `TAX_RATE_BPS`" habit are duplicated between T06's and
   T07's suites. Accepted parity — the duplication is cheap and keeps each suite independently readable.

Concrete adversarial probes a reviewer can run on top of the recorded gates (none of these are claimed as
executed here):

- Cancel an issued invoice after raising the product's stock to *exactly* `1_000_000 - qty` (should succeed —
  the guard is inclusive) and to `1_000_000 - qty + 1` (should answer `STOCK_OVERFLOW` and change nothing).
- Issue two drafts where the *first* line fails instead of the second (the rollback path is symmetric but is
  only pinned for the second line).
- Send `version: "0"` as a string (expect 422, because the schema rejects coerced strings — T02's design).
- Race an *issue* against a *cancel* of the same invoice: expect `[200, 409]` and one coherent state.

## Recap

- The invoice row is the claim; product rows are the ledger. `transitionInvoice` resolves the owned invoice,
  checks the edge (`assertTransition`) and the version, claims the move with a conditional `updateMany`, then
  deducts (issue) or restores (cancel) inside the same serializable transaction.
- Product writes are conditional (`quantityOnHand >= qty` / `<= 1_000_000 - qty`) and ordered by product id,
  so concurrent callers cannot oversell, cannot push stock past the database bound, and cannot deadlock on
  each other's locks; every stock change bumps the product `version`, which is what invalidates a stale
  manual edit.
- Any failure rolls back both the status claim and every earlier stock write — that is how "late line
  failure" and "overflow cancellation" stay atomic.
- Illegal and repeated transitions are 409 `INVOICE_NOT_EDITABLE` with a pair-specific message; deleted
  products are 404 naming the line; insufficient stock is 409 naming the product; a restore overflow is 409
  `STOCK_OVERFLOW`; stale versions are 409 `VERSION_CONFLICT`.
- 25 real-PostgreSQL cases cover the 12-pair matrix, deduction/restoration, rollback, ownership,
  authentication, origin, the error contract and four controlled races; the worker recorded red
  (`24 failed | 111 passed`) then green (`135`, then `136 passed`) plus unit 79/79 and lint/typecheck/build 0,
  all at `ce9c2ab`.
- Nothing here is accepted or merged: acceptance, the `--no-ff` merge and the independent verification are
  the coordinator's steps, and this document is a self-review written by the implementer.

## The big picture: T03 is the *join* task

T00 built the test infrastructure, T01 built the database contract, T02 built the vocabulary (schemas, DTOs, error/origin/cookie helpers). T03 is the first task that **uses all three at once**: it wires a real authentication provider to the real database through the real contracts, and it adds the demo seed. It adds no new table, no new error shape and no new money rule — its job is to make the previously-separate pieces actually cooperate, and to prove that cooperation against live PostgreSQL rather than mocks.

So the question T03 answers is not "does a product get created?" (T05) but: **"can a real browser session be created, read, revoked and expired through these four routes, with nothing leaking?"**

Two design choices before the details:

- **Real libraries, real database, real handlers.** The auth tests invoke the actual `app/api/auth/*/route.ts` functions with real `Request` objects, against real PostgreSQL, running real BetterAuth 1.7.5 with real bcryptjs hashes. Nothing about authentication is stubbed — which is why the tests can prove things a mock never could (an expired row in PostgreSQL *is* rejected; a copied cookie *does* stop working; a duplicate email *does* come back as a conflict even though we disabled automatic sign-in).

## Architecture and mental model

```
                       ┌──────────────── T02 (accepted) ─────────────────┐
  HTTP Request ──► app/api/auth/*/route.ts ──► lib/http.ts helpers
                       │  assertSameOrigin   │  readJson(schema)   │  forwardAuthResponse
                       │  registerSchema / loginSchema / emptyBodySchema  │  errorResponse (P2034→409)
                       └──────────┬──────────────────────────────────────┘
                                  ▼
                       lib/auth/server.ts  getAuth()  (lazy singleton)
                         ├── prismaAdapter(getPrisma())        ← T01 lib/prisma.ts → PostgreSQL
                         ├── emailAndPassword { hash, verify } ← T03 lib/auth/password.ts (bcrypt 12)
                         └── session { 7d, disableSessionRefresh, cookieCache off }
                                  ▼
                       lib/auth/session.ts  getSessionUser / requireAuth / requirePageUser
                                  ▼
                       Prisma models User / Account / Session (T01 schema + frozen migration)

  prisma/seed.ts  (plain `tsx`, no server-only imports) ──► PrismaClient + PrismaPg ──► User/Account/Product
```

Three boundaries a reader should notice:

- **`server-only` is the guard rail.** `lib/env.ts`, `lib/prisma.ts`, `lib/auth/server.ts` and `lib/auth/session.ts` start with `import "server-only"`, so a client component importing them breaks the build. The harness aliases `server-only` to a stub (`vitest.config.ts` → `tests/support/server-only.ts`), which is what makes them importable under vitest.
- **No catch-all route.** The plan deliberately exposes four explicit routes instead of mounting BetterAuth's `/api/auth/[...all]`, so unused auth surface (reset, OAuth callbacks) is unreachable. `git ls-tree` at the pin confirms only the four `route.ts` files exist under `app/api/auth/`.
- **Tests talk to handlers in-process, not over HTTP.** So `export const runtime = "nodejs"` is *not* exercised by tests; the `pnpm build` route table (`ƒ /api/auth/{login,logout,register,session}`) is the evidence that these routes compile and mount under Next.

## File-by-file walkthrough

### `lib/auth/password.ts` — one policy for hashing and byte limits (32 lines)

- Constants: `BCRYPT_COST = 12`, `PASSWORD_MIN_CODE_POINTS = 8`, `PASSWORD_MAX_BYTES = 72`.
- `validatePassword(password)`: throws `AppError(422, "VALIDATION_ERROR", …, { password: [...] })` when the string has fewer than 8 code points (`Array.from(password).length`, so `😀` counts as the one character a human sees) **or** more than 72 UTF-8 bytes (`new TextEncoder().encode(...).length`). It never trims — a leading space is part of a password, and trimming at registration but not at login is a classic "my password stopped working" bug.
- `hashPassword` → `bcryptjs.hash(password, 12)`.
- `verifyPassword({password, hash})` returns `false` for candidates over 72 bytes **before** handing them to bcrypt. *Why:* bcrypt silently ignores bytes past 72, so without this guard two different long passwords would authenticate the same account — a quiet, real vulnerability.

The `else if` shape is safe rather than sketchy: fewer than 8 code points can never exceed 72 bytes (7 × 4 = 28 max), so the two conditions cannot both apply in a way that matters.

### `lib/auth/server.ts` — where the library meets the database (54 lines)

`createAuth(env)` builds a `BetterAuthOptions` object (typed explicitly, because the inline literal breaks `ReturnType<typeof betterAuth>` assignability — a genuine TypeScript trap the card records) with:

- `baseURL`/`trustedOrigins` = `env.authUrl`, keeping **BetterAuth's own CSRF protection** in addition to T02's `assertSameOrigin`;
- `prismaAdapter(getPrisma(), { provider: "postgresql" })` — T01's lazy client, no second connection pool;
- `emailAndPassword.password = { hash: hashPassword, verify: verifyPassword }` — **bcryptjs instead of BetterAuth's default scrypt**. Plan-mandated, and it is what makes A4 verifiable: the stored `Account.password` is a `$2b$12$…` string that `getRounds()` can measure;
- `session.expiresIn = 604800` with `disableSessionRefresh: true` → a **non-sliding**, absolute 7-day lifetime;
- `session.cookieCache = { enabled: false }` → every session read consults PostgreSQL, which is exactly what makes immediate revocation (A3) and DB-backed expiry truthful;
- `advanced.useSecureCookies = env.authUrl.startsWith("https:")`.

`getAuth()` is cache-first (`instance ?? globalThis.stockflowAuth`), storing on `globalThis` only outside production so dev hot-reload doesn't build a new instance on every edit. Importing the module reads no env and opens no connection — that is what keeps the unit suites Docker-free.

### `lib/auth/session.ts` — three guards, one shape (30 lines)

- `getSessionUser(headers)` → `getAuth().api.getSession({ headers })`, narrowed to `{ id, email, name }`. Tokens, expiry and hashes never leave the module.
- `requireAuth(headers)` → `AppError(401, "UNAUTHORIZED", "Authentication required")`; used by the session route today and by T05–T07 next.
- `requirePageUser()` → reads Next's request scope (`await headers()`) and `redirect("/login")`. Documented as navigation-only: the plan's *"layout alone is not authorization"* rule means every data-bearing page still calls it.

### The four routes

| Route | Order | Contract |
|---|---|---|
| `POST app/api/auth/register/route.ts` | origin → body → sign-up → revoke → strip cookies | **201** public user; duplicate **409** `REGISTRATION_FAILED`; bad shape **422** with field paths; non-JSON **400** `INVALID_JSON`; foreign origin **403** `ORIGIN_REJECTED`; **never sets a cookie** |
| `POST app/api/auth/login/route.ts` | origin → body → sign-in | **200** user + session cookie; bad credentials → identical **401** `INVALID_CREDENTIALS` |
| `POST app/api/auth/logout/route.ts` | origin → empty JSON `{}` → sign-out | **204**, empty body, clearing cookies; harmless when already signed out |
| `GET app/api/auth/session/route.ts` | `requireAuth` → `dataResponse` | **200** `{id,email,name}` with `cache-control: no-store`, else **401**; never a raw token |

Two details carry most of the task's weight:

**"Disable automatic sign-in" without breaking duplicate detection.** BetterAuth's `signUpEmail` signs the caller in by default, and it only reports duplicate emails truthfully *while* that default is on. Switching `autoSignIn` off therefore makes duplicates look like successes — worse than a cookie, because it would tell the client "registered!" for an account that already exists. So the route keeps the default and cleans up after it: `revokeAutomaticSession()` reads the `Set-Cookie` values off BetterAuth's response, converts them to a `cookie` header (`name=value` pairs), and calls `getAuth().api.signOut({ headers, asResponse: true })`. Then `withoutCookies()` rebuilds the response carrying only the JSON body. Net effect: **no cookie reaches the client and no usable session row survives** — which is why the A1 test can assert both `getSetCookie() === []` and `session.count() === 0`.

**Origin first, writes second.** `assertSameOrigin(request)` runs *before* the body is parsed, so a foreign origin cannot even probe validation errors; the N6 test backs that with `user.count() === 0` / `session.count() === 0`. The comparison is exact equality against `BETTER_AUTH_URL` — never `startsWith`, and never `Origin` vs `Host`, both of which an attacker can satisfy or suffix-match.

### `prisma/seed.ts` — idempotent convergence (78 lines)

- Refuses `NODE_ENV=production` **before opening a connection**; requires `DATABASE_URL`; validates its own demo password through the same policy module.
- Builds its own client: `PrismaClient({ adapter: new PrismaPg({ connectionString }) })`. Deliberate and documented — `pnpm db:seed` runs `tsx prisma/seed.ts` (wired in T01's `prisma.config.ts`), i.e. plain Node, where `server-only` imports throw.
- Owner: look up `demo@stockflow.local`; if absent, create user + credential `Account` in **one nested write** (`providerId: "credential"`, `accountId: user.id`, `password: await hashPassword(DEMO_PASSWORD)` — the same hash BetterAuth will verify). If present but missing a credential account, add one and **never overwrite an existing hash**.
- Products: five `upsert`s keyed by the composite unique `userId_sku` with `update: {}` — so a rerun never resets stock, names, prices or soft deletion.
- `finally { await prisma.$disconnect() }`, plus a CLI guard (`process.argv[1]` vs `import.meta.url`) that sets `exitCode = 1`, so a failed seed cannot exit 0.

Demo data: `demo@stockflow.local` / `StockFlowDemo!2026`, and `DEMO-001`…`DEMO-005` (paper 749¢/120, pens 899¢/200, organizer 2450¢/40, mouse 2999¢/35, cable 1299¢/80) — the numbers T10's README must quote.

### `tests/helpers.ts` — the fixtures later tasks will reuse (79 lines)

`registerAndLogin()` drives the **real** routes (register then login) and returns `{user, cookie, email, password}`; `createProductFixture(userId, overrides)` writes **straight through Prisma** on purpose, because product fixtures must not depend on T05 routes that don't exist yet; `makeRequest` is re-exported from the T00 harness so successors have one import; and `withCookie`, `sessionCookieFrom`, `uniqueEmail`, `readErrorBody`, `FIXTURE_PASSWORD` round it out.

## Happy path, traced end to end

Using the harness values (`BETTER_AUTH_URL=http://localhost:3100`, a random secret, the leased test database):

1. **`POST /api/auth/register`** with `{"email":"  User-ABC@Example.com  ","password":"Fixture-Password-2026"}` and `origin: http://localhost:3100`. T02's schema trims and lowercases the email and enforces the password policy; BetterAuth inserts `User` + `Account` (bcrypt cost 12) + a `Session`; T03 signs that session out again and strips the cookies. Response: `201 {"data":{"id":"…","email":"user-abc@example.com","name":"user-abc"}}` with **no** `Set-Cookie`, and zero session rows left behind.
2. **`POST /api/auth/login`** with the same credentials → BetterAuth verifies the bcrypt hash, inserts **one** `Session` row, and returns `200` plus `Set-Cookie: better-auth.session_token=…; Path=/; HttpOnly; SameSite=Lax; Max-Age=604800` (no `Secure`, because the configured origin is plain http). `forwardAuthResponse` re-emits only `{id,email,name}` and appends each cookie individually — never comma-joined.
3. **`GET /api/auth/session`** with `cookie: better-auth.session_token=…` → `200`, `cache-control: no-store`, body exactly `{id,email,name}`.
4. **`POST /api/auth/logout`** with `{}` + `content-type: application/json` + the cookie → `204`, empty body, clearing cookies; the same cookie now yields `401 UNAUTHORIZED`, because PostgreSQL no longer has the session row.

Tooling path for the seed (there is no UI yet, so trace the command): `pnpm db:seed` → Prisma CLI reads `prisma.config.ts` (which loads `dotenv`) → `tsx prisma/seed.ts` → production guard runs before any connection → owner and five products converge → disconnect → exit 0.

## Correctness, edge cases and security

**Applied and evidenced**

- **A5 boundaries:** `😀`×8 accepted (8 code points / 32 bytes), `😀`×7 rejected, `é`×36 accepted (exactly 72 bytes), `é`×37 rejected, 73 ASCII bytes rejected, empty rejected — both directly through `validatePassword` and through the register route.
- **A4 salting:** hashing the same password twice yields different strings; `getRounds()` = 12; the stored value matches `/^\$2[aby]\$/` and never contains the plaintext.
- **A2 cookie hardening:** `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age=604800`, and explicitly **no `Secure`** on the plain-http test origin — so accidentally enabling secure cookies in dev would fail a test instead of silently breaking local logins.
- **A3 revocation:** logout → 204 + a `Max-Age=0` clearing header; the *copied* cookie then returns 401 and the session count is 0; repeating logout is still 204; a fresh login afterwards still works.
- **A9 non-enumeration:** wrong password and unknown email produce byte-identical `{"error":{"code":"INVALID_CREDENTIALS","message":"Invalid email or password"}}`, no cookies, no session rows.
- **Expiry is data, not just crypto:** the test backdates `expiresAt` in PostgreSQL and the correctly-signed cookie is rejected — only possible because the cookie cache is off. A second assertion proves a session read does **not** move `expiresAt` (non-sliding).
- **N6 origin identity:** foreign, missing, `"null"`, empty, trailing-slash (`http://localhost:3100/`) and `.evil` origins all 403 `ORIGIN_REJECTED`, with no rows written.
- **Mass assignment:** an extra `userId` key in the register body is a 422 naming the field (`z.strictObject`), rather than a silently accepted owner.
- **Sanitized failures:** every route body runs inside `handleRoute`, so an unexpected throw becomes the opaque 500 `INTERNAL_ERROR`; only 4xx responses carry detail.

**Where the risk actually lives** (decisions #3 and #4 are now settled — see *Open decisions*; the remaining notes are follow-ups)

- ~~`revokeAutomaticSession()` is awaited without a `try/catch`, so a BetterAuth sign-out failure would surface as a 500 after the rows are committed.~~ **Hardened at `479a347`** (test-first): cleanup is now best effort, so the worst case is 201 + no cookie + an unreachable, expiring session row. Registration still necessarily writes and deletes a session row — two extra round-trips per signup — which is accepted.
- The password policy now exists in **three** places: T02's Zod schemas (literal `8` / `72`), T03's exported constants (also fed to BetterAuth), and BetterAuth's `minPasswordLength`/`maxPasswordLength`. They agree today and both paths are tested, but nothing forces them to stay in step.
- ~~`useSecureCookies` keys off `BETTER_AUTH_URL`'s scheme, so an `http:` production URL would issue non-Secure cookies.~~ **Accepted as a constraint** (decision #4): correct behind an https-terminating proxy, loud rather than silent when misconfigured, and `NODE_ENV`-keying would break an http-served deployment.

**Not applicable in T03:** money rounding/overflow and stock atomicity (T02, T06–T07), invoice state machine (T07), pagination (T05+), and cross-user resource scoping — the plan's "another user's id → 404" rule is simply not reachable from these four routes.

1. **[RESOLVED — user decision, 2026-09-18] `name` semantics.** The plan's decision bullet was the stale half: it said *"supply BetterAuth's required name as the normalized email"*, while `nameFromEmail()` stores the **email local part** (`user-abc` for `user-abc@example.com`, capped at 200 chars, falling back to `"StockFlow user"`). 2. **[RESOLVED — user decision, 2026-09-18] Docs placement/ownership.** The branch carries commit `38e3ff3` (`agent_explanations.md` → `agent_explanations/{T00,T01,T02}.md`), which is outside T03's graph-owned paths. It was explicitly requested by the user in the dispatch and honestly disclosed in the card, and the content is verified byte-identical. **Resolution:** both docs were placed **on the T03 branch** before the merge — `agent_explanations/T03.md` and the one-line `implementation_plan.md` amendment in a single documentation-only commit — with the gates re-run at that revision and the card updated to cite it. The reviewed pin therefore moved: the coordinator must merge the **new tip**, not `1f07293`, and treat the extra commit as documentation (no executable file changed). The split itself (`38e3ff3`) still rides along with the T03 merge as user-directed work outside T03's owned paths.
3. **[RESOLVED — user decision, 2026-09-18] Unguarded post-write call in registration.** `revokeAutomaticSession()` was awaited without `try/catch`, so a BetterAuth `signOut` failure returned 500 *after* the account was committed (a retry then hit 409 "duplicate"). **Resolution: hardened at `479a347`**, test first — `5afea18` added an integration case that stubs `signOut` to reject and asserts 201 + no `Set-Cookie`; against the unhardened route it failed exactly as intended (`AssertionError: expected 500 to be 201`, run output `1 failed | 26 passed`), and after the fix the file passes 27/27. The catch logs a fixed message with no cookie/token material. Why 201 is the right answer rather than 500: the client never received the token, so the residual session row is unreachable and expires with the 7-day lifetime, whereas a 500 would invite a retry that reports a confusing duplicate-email conflict. Registration still writes and deletes a session row (two extra round-trips per signup) — accepted.
4. **[RESOLVED — user decision, 2026-09-18] `useSecureCookies` keyed on the URL scheme — accepted as a constraint.** The concern was that `env.authUrl.startsWith("https:")` plus an `http:` `BETTER_AUTH_URL` (which `readEnv` accepts) would issue non-Secure cookies in production. Analysed for the intended deployment (TLS terminated by a proxy such as Traefik, Node container behind it): **not an issue**, and my original framing was too alarmist. With `BETTER_AUTH_URL` set to the public `https://` origin — which is also what the origin check needs — `useSecureCookies` is `true`, BetterAuth switches to the `__Secure-` prefixed cookie name, and the browser's TLS hop through the proxy means those cookies are both accepted and returned; the plain-HTTP proxy→container hop is irrelevant because `Secure` is enforced by the browser. Conversely an `http://` baseURL cannot silently downgrade: the browser's `Origin` (`https://…`) would no longer equal the configured URL, so `assertSameOrigin` 403s every mutation — a loud break. And the alternative "fix" of keying `Secure` off `NODE_ENV` would *break* any http-served deployment, because browsers drop `Secure` cookies sent over http. Residual risk is confined to a deliberately all-HTTP production deployment, where the flag would not help anyway. Consequence for documentation: **T10 must state both cookie names** — `better-auth.session_token` over http and `__Secure-better-auth.session_token` over https.
5. **Two hygiene items, follow-ups rather than blockers.** (a) The card says login sets *"one HttpOnly session cookie"*, but the pinned test only inspects `getSetCookie()[0]` — it never asserts the header count is 1 (it asserts the session-row delta instead). Either soften the wording or add the count assertion later. (b) The password policy is duplicated across T02's Zod literals and T03's exported constants — worth consolidating once, by whoever owns the contract.

## The transferable lessons

1. **A flag is a promise you have to keep cleanly.** "Registration must not sign the user in" cannot be implemented by turning the library's auto sign-in off, because that flag also gates duplicate detection — you end up with false 201s. Keeping the flag and undoing its side effect (revoke the session, strip the cookies) is more work and more honest.
2. **Test the dangerous library assumption, don't trust it.** BetterAuth's sign-out route revokes with a cookie header alone; that was verified against the installed version before the design leaned on it, and the A1 test asserts the *database* consequence (`session.count() === 0`), not just the response.
3. **A cookie cache is an invisibility cloak over revocation.** `cookieCache: { enabled: false }` is what lets an expired or revoked session die on the next request. If it were on, every A3 assertion would be a lie with a 7-day fade-out.
4. **Prove the absence of writes.** Foreign-origin tests assert `user.count() === 0`, not just `403`. "It rejected the request" and "it did not touch the database" are different claims, and the second is the one that matters.
5. **Fail closed in the harness, then you can trust the suite.** `tests/setup.ts` refuses to run against anything but the leased test database, and `fileParallelism: false` keeps shared data deterministic; a suite that can silently point at the wrong database is worse than no suite.
6. **Idempotent means "converge", not "re-run".** `update: {}` upserts plus never-rewrite-credentials semantics are what make `pnpm db:seed` safe on a database somebody has already been using.
7. **Environment quirks are evidence too.** The `NODE_ENV=development`-exported-in-the-shell build failure (`/_global-error` prerender) is not T03's code, but recording it — including the honest note that a clean baseline could not be established — saves the next agent an hour.
8. **A review is not a re-run.** Distinguishing "worker-recorded at SHA X" from "independently executed" is the difference between a handoff and a guess; the coordinator's merged-revision run is what converts REVIEW into DONE.
9. **Spec drift hides in the fields nobody asserts.** The `name` question surfaced only because the plan text was read side-by-side with the code; `expect.any(String)` will happily accept the wrong string for the rest of the project.

### Recap

T03 plugs four explicit auth routes into T01's database and T02's contracts via BetterAuth with bcryptjs (cost 12), no cookie cache, a fixed 7-day non-sliding session and per-route exact-origin checks. Registration never signs you in, and duplicates still report an honest 409. Logout deletes the session row, so a copied cookie dies immediately. Everything unexpected degrades to an opaque 500, and never to a token, hash or SQL detail. A single `seed()` converges a demo owner plus five products without ever overwriting stock or credentials, refuses to run in production, and fails loudly. The tests are 31 real-PostgreSQL integration tests through the actual handlers (56 across the suite) with a genuine red phase that caught the register cookie, the extra sessions and the missing origin enforcement — plus a post-review red (`expected 500 to be 201`) that hardened the cleanup path. All four review decisions are settled (#1 plan-amended, #2 docs on the branch, #3 hardened test-first at `479a347`, #4 accepted as a deployment constraint) — but T03 is still **REVIEW, not DONE**: the coordinator must merge the branch tip and re-verify the merged revision before T04/T05 start.

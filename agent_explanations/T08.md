## 1. Summary

T08 turns the already-shipped products API (T05) into the first screens a user can actually work in.
It adds three server-rendered routes under the dashboard shell — the list, the create form and the
edit form — plus the two client components those routes mount. There is no new API surface, no schema
change and no shared-file edit: the pages read through T05's service, and every mutation goes back
through the documented REST endpoints, so the authorization, versioning and money rules stay in one
place. F2 (product CRUD/search/pagination/empty state), F5 (every dashboard page redirects
unauthenticated visitors) and F6 (pending disables resubmit, failures show retry, not a blank page) are
the mapped requirement IDs.

## 2. Requirements and scope

In plain terms:

- **F2** — a signed-in user can list their own products, search by name or SKU, page through them, see
  a sensible empty state, create, edit and delete.
- **F5** — `/products`, `/products/new` and `/products/[id]/edit` each refuse an unauthenticated
  visitor (fresh, expired or revoked session) and never render private rows.
- **F6** — while a request is in flight the submit/delete controls cannot be used twice; a failure shows
  a message the user can act on (including a retry) instead of a blank screen, and typed values survive.

Delivered: all three deliverables on the card (list/search/pagination/delete screen; create/edit forms
with per-page session checks; the products reviewer checklist rows).

Deliberately not in this task: no invoice screens or product picker (T09); no new API, schema,
migration or dependency (T05/T01 own those); no shared UI/helper changes (T04 owns
`components/ui/**`, `lib/client-api.ts`, `components/pagination.tsx`, `lib/money.ts`); no browser test
suite, because AMEND-T04-1 removed the Playwright layer and moved F1–F6 to the manual reviewer
checklist; and no automated test file, because no test path is graph-owned for T08 (section 6 explains
what stands in for it).

## 3. Architecture and mental model

StockFlow's layering is App Router page → service → Prisma for reads, and client form → REST route →
service → Prisma for writes. T08 sits on both halves without inventing a third:

```
Browser
  │
  ├─ GET /products?search=…&page=…          (navigation; client-side once hydrated)
  │     app/(dashboard)/layout.tsx           requirePageUser()  → nav + LogoutButton
  │     app/(dashboard)/products/page.tsx    requirePageUser() again
  │           productListSchema.safeParse({ page, search })     (T02's strict schema)
  │           listProducts(user.id, query)  ───────────────►  lib/services/products.ts (T05)
  │           <ProductList page={…} search={…} />               (client component, plain DTOs)
  │
  └─ DELETE /api/products/:id  { version }   (client call from ProductList)
        app/api/products/[id]/route.ts       requireAuth → assertSameOrigin → parseId → readJson
              deleteProduct(user.id, id, { version }) ──────►  withSerializableRetry (T01)
              router.refresh() re-renders the server page instead of patching rows locally
```

Two boundaries are worth naming for a junior reader. First, a **server component** runs only on the
server and can hold secrets and database access; a **client component** (`"use client"`) is shipped to
the browser and may only receive serializable props. T08's pages are server components that check the
session and fetch rows; the two components they mount are client components that receive
`ProductDto`/`Page<ProductDto>` values (plain strings and numbers, no Prisma types). Second, the
dashboard **layout is not authorization**: it checks the session to decide what navigation to draw,
and each page checks again before loading its own data (as `systemPatterns.md` and T04's card require),
which is why every one of the three new pages calls `requirePageUser()` itself.

The only state T08 owns is form state and the small delete/notice state inside the two client
components. Everything else — which rows exist, what a product's current `version` is, what the price
in cents is — comes from the server, so the UI never becomes a second source of truth.

## 4. Implementation walkthrough

### 4.1 The list page — `app/(dashboard)/products/page.tsx` (95 lines)

This is a server component; it renders once per request on the server and never ships to the browser.
Its exports are `metadata` (the per-page title that T04's root layout formats as `Products · StockFlow`)
and the default async page.

- **`productsHref(search, page)` (lines 18-24)** builds the canonical list URL: the search term only when
  present, `page` only when greater than 1. Keeping page 1 parameter-free means the "clean" list has one
  canonical address, which is also what the stale-page clamp redirects to.
- **Session first (line 32).** `requirePageUser()` reads the session from the database through the
  request scope and redirects a visitor with no valid session to `/login`. It runs *before* the page
  reads `searchParams` or touches the database, so F5 holds even if the layout check were bypassed.
- **Query parsing (lines 33-40).** In Next 16 `searchParams` is a Promise, hence the `await`. Only two
  keys are forwarded to T02's strict `productListSchema`: `page` and `search`, and only when they are
  strings (a repeated key arrives as an array and is ignored). This matters because the schema is a
  `strictObject` — feeding it the whole query object would turn harmless extras such as `?created=1`
  into a validation error, and those extras are exactly how the two success notices travel.
- **Invalid input, not a crash (lines 54-69).** If the parse fails (`?page=abc`, `?page=0`), the page
  renders the header plus a destructive alert and a "Reset the list" link, and never issues a query.
  A reviewer should read this as "the list is usable in every state": no blank page, no 500.
- **Loading rows (line 72).** `listProducts(user.id, parsed.data)` is T05's owner-scoped service called
  directly, not an HTTP self-fetch. That is the architecture the plan asks for ("server pages validate
  sessions without HTTP self-fetches"); `parsed.data` also carries the schema default `pageSize: 20`,
  so the page and the API cannot disagree about the page size.
- **The stale-page clamp (lines 74-77).** If the requested page is past the last one — the common case
  being "I deleted the only row on page 3" — the page redirects to the last real page instead of
  rendering an empty table above pagination reading "Showing 41–40 of 40". Because the dashboard shell
  has already been streamed when this runs, Next emits that redirect client-side (see observation O3 in
  section 7); the rendered behaviour is still "you land on a real page".
- **Render (lines 79-95).** Header with the "New product" call to action, the `?created=1`/`?updated=1`
  notices rendered as `role="status"` alerts (an announcement, not an error), then `<ProductList>`
  handed the page of DTOs and the committed search term.

### 4.2 The list itself — `components/product-list.tsx` (213 lines)

`"use client"` because search, delete, pending state and notices all need the browser. The rows still
arrive as props from the server render; the component never fetches a list, so there is no second data
path that could disagree with the server.

- **Props (lines 28-33)** are deliberately serializable: a `Page<ProductDto>` and the committed search
  string. The search string is passed down rather than read from `useSearchParams()` so the rendered box
  can never disagree with the rows on screen.
- **Delete state (lines 44-49).** `pendingId` is the id of the row whose delete is in flight; every
  delete control in the table is disabled while it is set and that row shows "Deleting…", which is F6's
  "pending disables resubmit" applied to the list. `deletedNotice`, `failure` and `retryTarget` carry the
  outcome.
- **`confirmDelete` (lines 51-75)** is the interesting function. It sends `{ version }` — the version of
  the row the user actually saw — to `DELETE /api/products/:id`, and handles four outcomes:
  - `204`: show "… was deleted." and `router.refresh()`, so the server decides what the list now looks
    like (including re-triggering the clamp when the last row of the last page went away).
  - `409 VERSION_CONFLICT`: the row changed elsewhere. Nothing was deleted, so it refreshes and asks the
    user to review the new state; it deliberately does **not** retry with the stale version.
  - `404`: already deleted elsewhere; explain and refresh.
  - anything else (network failure, which `apiFetch` reports as status 0, or a 5xx): show the message and
    keep the row in `retryTarget` so an explicit "Try again" is possible.
  `finally` clears `pendingId` either way, and the `if (pendingId) return` guard at the top makes a
  double submission impossible even before React disables the buttons.
- **Search form (lines 79-92).** `next/form`'s `<Form action="/products">` is an ordinary GET form, so it
  works before hydration and navigates client-side once hydrated; the dashboard's `loading.tsx` skeleton
  shows during the transition. Only the `search` input lives inside the form, so submitting resets `page`
  to 1 — searching should never strand the user on page 4 of the old result set. The "Clear" control is a
  plain link to `/products`, rendered only while a search is active.
- **Notices (lines 94-112).** Success is an `Alert role="status"`; failure is a destructive `Alert` with
  the message and, when the failure is retryable, a "Try again" button.
- **Two different empty states (lines 114-136).** "No products match …" plus a clear-search link when a
  search is active, versus "No products yet." plus "Add a product" for an empty catalogue. They are
  separate because the useful next action differs.
- **Table (lines 139-206).** A real `<table>` from the T04 kit with `scope="col"` headers. Prices go
  through `formatMoney` (T02's pure cents formatter) instead of a locale formatter, which keeps server and
  client output identical and avoids a hydration mismatch. Row actions carry accessible names
  (`Edit DEMO-001`, `Delete DEMO-001`) because a column of identical "Edit" links is useless to a screen
  reader.
- **Confirmation dialog (lines 176-200).** `AlertDialog` names the SKU, states the consequence ("the SKU
  stays reserved; invoice lines keep their snapshot") and offers Cancel plus a destructive "Delete
  product". Radix closes the dialog on the action click and `confirmDelete` takes over; the row state
  communicates progress.
- **Pagination (lines 207-209)** reuses T04's `Pagination` with `query={{ search }}`, so Previous/Next
  keep the filter and `?page=` stays the single source of paging truth.

### 4.3 The form — `components/product-form.tsx` (336 lines)

One component serves both screens. `ProductFormProps` (line 15) is a discriminated union, so an edit form
cannot even be constructed without a product, and `const product = props.mode === "edit" ? props.product : null`
(line 87) is the single switch that decides payload shape, labels and the concurrency hint.

- **Pure helpers first.** `centsToInputValue` (lines 24-26) turns integer cents back into the decimal
  string `parseMoney` expects using `Math.trunc`/`%` — no float round-trip, so `749` becomes `7.49` and
  parses back to `749` exactly. `valuesFromProduct` (29-37) maps the server DTO into form strings
  (`description: null` → `""`), `fieldMessage` (40-42) pulls the first message for a field path, and
  `messageOf` (44-46) keeps a thrown message but always has a fallback.
- **`buildSubmitBody` (lines 53-78) is payload construction, not a second validator.** It reports only
  what cannot be sent at all: the price string goes through T02's shared `parseMoney` (whose thrown
  message is reused verbatim), and the quantity must match `^\d+$`. Everything else — SKU length, name
  rules, bounds, duplicates, ownership, stock — is left to the server, which is what the card means by
  "no client-only validation claims". An empty description becomes `null`, the documented "clear" value.
  `version` is added only in edit mode, because `createProductSchema` is a `strictObject` that would
  reject an unknown `version` key on create.
- **State (lines 87-95).** `values`, `version`, `pending`, `reloadPending`, `notice`, `failure`,
  `fieldErrors` and `reloadFailed`. Values live in React state, which is exactly how F6's "preserves
  entered values" is satisfied: a failed request re-renders with the same object.
- **`reloadLatest` (lines 111-134)** is the conflict-refresh path. It GETs the product, overwrites
  `values` and `version` with the saved row, clears field errors, and posts a `role="status"` notice
  explaining that saving stopped and the form now shows the latest saved values. If that reload itself
  fails it sets `reloadFailed`, which renders an explicit "Load the latest values" button (the retry the
  card asks for); a 404 during reload reports that the product no longer exists.
- **`handleSubmit` (lines 136-175).** On a build error it sets inline field errors plus "Check the
  highlighted fields and try again" and returns **without issuing a request**. Otherwise it sets
  `pending`, clears the messages, and sends `POST /api/products` (create) or
  `PATCH /api/products/:id` with the version (edit) through `apiFetch`. On success it calls
  `router.push("/products?created=1" | "?updated=1")` and deliberately leaves `pending` true — the submit
  button must not become clickable again while the page navigates. On `ApiClientError` it maps the
  server's `fields` onto the inputs and shows the message; a `VERSION_CONFLICT` in edit mode is routed to
  `reloadLatest()` rather than left as a dead end.
- **Markup (lines 177-331).** `<form onSubmit={handleSubmit} aria-busy={pending} noValidate>`: `noValidate`
  is deliberate because the server owns validation and native bubbles would hide the inline messages.
  Every field is `Label` + `Input`/`Textarea` + hint + conditional inline error wired with
  `aria-invalid` and `aria-describedby`, so a screen reader hears the reason next to the control. Price
  uses `inputMode="decimal"` and quantity `inputMode="numeric"` for the right mobile keyboard. In edit
  mode the footer of the fields shows "Loaded version N: saving sends this version, so a product changed
  elsewhere is reported instead of overwritten" — the concurrency contract is visible on screen, not just
  in the code. The buttons are the submit button (text switches to "Saving…", `disabled` and `aria-busy`
  while pending) and a "Back to products" link.
- **Small latent risk (O8 in section 7):** `EMPTY_VALUES` (line 21) is a module-level object used as the
  create-mode initial state. It is safe today because every update spreads into a new object, but nothing
  stops a future edit from mutating it in place and leaking values between form instances.

### 4.4 The two form pages — `new/page.tsx` (22 lines) and `[id]/edit/page.tsx` (45 lines)

`new/page.tsx` is intentionally tiny: metadata, `await requirePageUser()`, a heading and
`<ProductForm mode="create" />`. The page owns authorization; the form owns state; the discriminated
union means the create screen cannot accidentally hand over a product.

`[id]/edit/page.tsx` adds the data load and two deliberate guards:

- `domainIdSchema.safeParse(id)` (line 25-26) before `getProduct(user.id, parsedId.data)` (line 30). The
  service feeds the id straight into a Prisma query against a `uuid` column, so a malformed segment such
  as `/products/abc/edit` would otherwise reach the driver and surface as a 500 through the error
  boundary. Validating first turns it into a clean "this page does not exist". The schema also
  lower-cases, matching T05's normalization of upper-case UUIDs.
- A 404 from `getProduct` becomes `notFound()` (line 32). T05's *API* answers 422 for a malformed id
  because for an endpoint that is malformed input; for a *page* the same condition means "no such
  screen". Using not-found for malformed, unknown, unowned and soft-deleted ids alike also means the
  page cannot be used to probe which UUIDs exist (A7), and a product deleted between the list render and
  the click never renders a form for a row that is gone.

### 4.5 End-to-end happy path (illustrative inputs, not a claim that this exact run was executed)

1. Signed-out visitor opens `/products` → the dashboard layout's `requirePageUser()` redirects to
   `/login`; the same holds for `/products/new` and `/products/<uuid>/edit` (F5).
2. They sign in with the seeded demo credential. The `(auth)` layout's signed-in redirect lands them on
   `/products`, where `requirePageUser()` resolves the session from the database and `listProducts`
   returns five seeded rows newest-first; the table shows SKU, name, `$7.49`-style price and stock with
   "Showing 1–5 of 5".
3. They type `DEMO-002` into the search form and submit → GET `/products?search=DEMO-002`; the strict
   schema trims it, the service escapes LIKE metacharacters and filters `userId` + `deletedAt: null`, and
   one row renders with "Showing 1–1 of 1"; the box keeps the term and a "Clear" link appears.
4. They click "New product" and enter SKU `paper-2`, name `Copy paper`, price `12.34`, stock `7`. On
   submit `parseMoney("12.34")` yields `1234`, so the payload is
   `{ sku: "paper-2", name: "Copy paper", description: null, unitPrice: 1234, quantityOnHand: 7 }` and the
   request is `POST /api/products` → `201` with the SKU stored as `PAPER-2` and `version: 0`. The client
   navigates to `/products?created=1`, where the server render shows "Product created." above the list.
5. They open that row's Edit link → `/products/<uuid>/edit` re-checks the session, loads the owned row and
   renders the form with `value="12.34"` and "Loaded version 0".
6. They change the price to `49.99` and save → `PATCH` with `version: 0` → `200` (`version: 1`) → back on
   the list with "Product saved.".
7. Had another tab already saved that product, step 6 would be `409 VERSION_CONFLICT`: the form keeps the
   typed values, explains that saving stopped, and loads version 1 into the fields (or offers "Load the
   latest values" if that reload failed). Nothing is silently overwritten.
8. They delete the row from the list → confirmation dialog → `DELETE { version: 1 }` → `204` →
   "PAPER-2 was deleted." and `router.refresh()`. The row disappears, the SKU stays reserved (creating it
   again answers 409 with `fields.sku`), and any existing invoice line keeps its saved snapshot.
9. At any point a revoked or expired session is caught by the next page render (`requirePageUser`) or by
   the next API call (401 → `apiFetch` navigates to `/login`), so no private content renders afterwards.

## 5. Correctness, edge cases and security

**Authorization and session (F5).** Each page calls `requirePageUser()` itself, and that helper resolves
the session from the database on every request (T03's `getSessionUser` → BetterAuth with request
headers). A cookie alone is therefore never enough: a deleted session row, an expired session or a logout
elsewhere is caught on the next render. The layout's check is a convenience for drawing navigation, not
the guard — that is the deliberate "layout is not authorization" rule from `systemPatterns.md`.

**Ownership (A7 through the F2 screens).** Every read goes through T05's owner-scoped service
(`getProduct(user.id, id)`, `listProducts(user.id, …)`), so a foreign row is structurally unreachable.
The UI cannot even name another user's id: the list only renders the owner's own rows, and the edit page
answers the same not-found for malformed, unknown, unowned and soft-deleted ids, so it cannot be used as
an existence oracle. `ProductDto` carries no `userId`, so no ownership data leaks into the browser
props either.

**Concurrency.** The client always sends the `version` it rendered — with `PATCH` and with `DELETE` — and
never retries a failed compare-and-swap by itself. A loser gets `409`, and the UI's response is always
"refresh the truth, then let the human decide": reload the product into the form for an edit, refresh the
list for a delete. That keeps the optimistic-locking guarantee T05 built in `withSerializableRetry`
intact all the way to the screen.

**Precision.** Prices cross the boundary as decimal strings typed by the user, are converted once by
`parseMoney` into integer cents, and are displayed by `formatMoney`. `centsToInputValue` uses integer
division and modulo, so the prefill round-trips exactly instead of accumulating binary-float error.
Nothing in T08 multiplies, sums or taxes money — that is T06/T07's territory.

**Validation split.** The page applies T02's strict schema to the query parameters it accepts; the form
converts only what it must to build a payload; every business rule (SKU uniqueness, bounds, length,
ownership, soft-delete) stays on the server, whose `fields` map is rendered inline next to the right
input. No "the client already checked that" claim exists anywhere in this task.

**Failure paths, concretely:**

| Situation | What the user sees | Why it is safe |
|---|---|---|
| Expired/revoked session on a page | `307` to `/login` | `requirePageUser()` resolves the session per request; the layout is not the only check |
| Session dies while a form is open | navigates to `/login` | `apiFetch` sends 401s from protected endpoints to `/login` (auth entry points excluded) |
| Duplicate SKU | alert plus inline "This SKU is already in use" under SKU | the server's `fields` map is rendered, not re-derived client-side |
| Stale version on save | "The product was not saved" + explanation; form reloaded to the latest values | `409 VERSION_CONFLICT` → `reloadLatest()`, no blind retry |
| Stale version on delete | "… changed since this list was loaded, so nothing was deleted" + refreshed list | refresh then re-decide |
| Product deleted in another tab while editing | "Product not found" + Back to products | `404` from `PATCH` |
| `?page=` past the last page | lands on the last real page | clamp before rendering rows (caveat O3) |
| `?page=abc` or `?page=0` | alert with "Reset the list" | strict schema; no query is issued |
| Malformed/unknown/foreign product id | 404 page, `noindex` | `domainIdSchema` + `notFound()`; no existence leak |
| Network failure during delete | destructive alert + "Try again" | `ApiClientError` status 0 kept with `retryTarget` |
| Render-time failure while listing | `(dashboard)/error.tsx` with "Try again" | T04's boundary, unchanged by this task |

**Explicitly not asserted by this review** (so nobody reads this as coverage): invoice issue/cancel stock
effects (T06/T07), currency selection, roles beyond per-user ownership, rate limiting, hard delete or
restore, and any browser-level interaction assertion — the latter by AMEND-T04-1's decision. No XSS
surface is added: all values render through JSX escaping, and `apiFetch` can only navigate to the fixed
`/login` path, never to a value from a response.

**What the matrix is worth, and what it is not.** It is a `curl` script (appendix A) that drives the real
dev server with a session cookie jar. It is not a unit test and not a browser: it asserts status codes and
rendered HTML text (after stripping React's `<!-- -->` text separators), not clicks. It answers the
questions a reviewer would otherwise click through for the read paths and the API calls these components
make, and it pins the two framework behaviours below. It cannot assert focus management, hover/disabled
styling, or that a disabled control really blocks a second click — those remain the card's reviewer rows.

**Independence caveat.** The matrix was written and run by the same agent that wrote the code, in the same
worktree, and section 6 *quotes* it rather than re-executing it (this review ran no application tests, by
the skill's default and since no lease was requested for it). A reviewer who wants independent evidence
should re-run appendix A or the integration suite from their own worktree.

**Two framework behaviours the matrix pins — documented by Next, not defects:**
1. `notFound()` in a **streamed** response renders the 404 UI with HTTP **200**. The not-found docs state:
   "Next.js will return a `200` HTTP status code for streamed responses, and `404` for non-streamed
   responses", and the rendered page carries `<meta name="robots" content="noindex" />`. The matrix
   therefore asserts the 404 *UI*, and this is why `/products/<id>/edit` answers 200 in dev. A production
   build could behave differently; nobody has measured that, so T10 should record it as observed, not
   guaranteed.
2. `redirect()` in a **streaming** context emits the redirect for the client (the redirect docs: "this
   will insert a meta tag to emit the redirect on the client side"). The stale-page clamp shows up as
   `NEXT_REDIRECT;replace;/products;307` in the payload plus
   `<meta http-equiv="refresh" content="1;url=/products"/>`, which is also what a JavaScript-less visitor
   follows. That is why the matrix asserts those markers rather than a `307`.

**Evidence durability.** The matrix script and log lived in `/tmp` — not durable, not committed — while
the card recorded the results in prose. This walkthrough closes that gap by publishing the reproduction
steps in appendix A, so the claim can be re-derived without the original files.

## 7. Reviewer checkpoints, observations and open questions

Nothing below is a correctness defect found by reading the pinned revision: the screens, guards, payloads
and error paths match what the card claims. These are the things a reviewer should look at, plus the
oddities worth recording before acceptance. O1–O7 are polish/robustness, O8 is a latent style risk, O9–O10
are evidence and framework notes.

- **O1 — the success notices are sticky in the URL** (`products/page.tsx:34-35, 82-91`). `/products?created=1`
  keeps the flag, so a reload or bookmark re-shows "Product created." / "Product saved.". Cosmetic, and the
  same trade-off T04 already accepted for `/login?registered=1`; a one-line `router.replace("/products")`
  after the notice renders would remove it.
- **O2 — two builders for one list URL** (`products/page.tsx:18-24` vs the private `pageHref` inside
  `components/pagination.tsx`). The clamp builds its own query string because the pagination helper is not
  exported, so changing paging semantics means changing two places. Maintainability only; T04 owns the
  pagination file, so consolidating belongs to a task that may touch it.
- **O3 — the clamp is a streaming redirect** (`products/page.tsx:74-77`), hence HTTP 200 plus a client-side
  redirect (framework note 2 in section 6). The rendered behaviour is correct; a JavaScript-less visitor
  waits out the 1 s meta refresh. Recorded so the 200 is not misread as a bug.
- **O4 — `notFound()` answers 200 in a streamed response** (`[id]/edit/page.tsx:26, 32`; framework note 1).
  The 404 UI is correct and carries `noindex`.
- **O5 — the products form pulls `zod` into the browser bundle.** `components/product-form.tsx:12` imports
  `parseMoney` from `lib/money.ts`, which imports `AppError` from `lib/http.ts`, which imports `zod`. That is
  functionally fine (no `server-only` guard on that chain, and `assertSameOrigin` is never called
  client-side) and the plan mandates the shared money helper, but the client bundle ships a schema library
  it does not use. Bundle size only; a future task could move `AppError` into a zod-free module.
- **O6 — the delete dialog closes before the request resolves** (`components/product-list.tsx:176-200`), so
  the in-flight state is the row's "Deleting…" text rather than a spinner inside the dialog. Deliberate:
  fighting Radix's close-on-action behaviour was not worth the complexity, and the `pendingId` guard plus
  the disabled controls already make double submission impossible.
- **O7 — delete notices and errors survive a client-side navigation** (`components/product-list.tsx:46-48`).
  React keeps the component instance across a `?search=` navigation, so "… was deleted." (or a delete error)
  can still be on screen after the user changes the search. Harmless, but clearing that state when the
  `page`/`search` props change (or keying the component) would scope it.
- **O8 — `EMPTY_VALUES` is a shared module object** (`components/product-form.tsx:21, 88`). Safe as written
  because every update spreads into a new object, but a future in-place mutation would leak values between
  form instances; returning a fresh object from the initializer is the cheap fix.
- **O9 — the evidence script is not committed** (section 6 and appendix A). This walkthrough publishes the
  steps, but the script itself has no home in the repository, and T08's graph-owned paths do not include
  one — so committing it would need a newly authorized task.
- **O10 — a product's not-found page sits outside the dashboard shell.** No `app/(dashboard)/not-found.tsx`
  exists (T04 shipped the root one), so a malformed, unknown, foreign or deleted product id renders the root
  404 without the app navigation. Cosmetic; whichever task next owns dashboard boundaries can improve it.

### Appendix A — reproducing the live matrix

Prerequisites: the `postgres-test` lease or another dedicated PostgreSQL, Docker reachable via
`sg docker -c` in this session, and a leased dev port (3100 was the granted one; the retired `next-e2e`
lease used the same port). All steps run from the task worktree.

1. Ensure the shared test service is up (it is normally already running):
   `sg docker -c 'docker compose --profile test up -d --wait postgres-test'`
2. Create a dedicated database so the matrix never touches the shared dev database on 5432:
   `sg docker -c 'docker compose --profile test exec -T postgres-test psql -U stockflow -d postgres -c "DROP DATABASE IF EXISTS stockflow_t08;" -c "CREATE DATABASE stockflow_t08;"'`
3. Migrate and seed it (the seed makes the demo credential and five products available):
   `DATABASE_URL=postgresql://stockflow:local_test_only@localhost:5433/stockflow_t08 pnpm db:migrate`
   `DATABASE_URL=postgresql://stockflow:local_test_only@localhost:5433/stockflow_t08 pnpm db:seed`
4. Start the app against that database. `.env` supplies the remaining variables, but `BETTER_AUTH_URL`
   must equal the origin the checks use or every mutation is 403:
   `DATABASE_URL=…@localhost:5433/stockflow_t08 BETTER_AUTH_URL=http://localhost:3100 nohup pnpm dev --port 3100 > /tmp/t08-dev.log 2>&1 &`
   then poll `curl -s -o /dev/null -w '%{http_code}' http://localhost:3100/login` until it returns 200.
5. Save the script below as `/tmp/t08-matrix.sh` and run `bash /tmp/t08-matrix.sh`. It prints one line per
   check and exits non-zero if any check fails; the recorded run was **67 checks, 0 failures**. It uses a
   fresh SKU per run, so it stays idempotent.
6. Clean up: stop only your own dev server (`kill -TERM` the `pnpm dev` → `sh -c next dev` → `next dev` →
   `next-server` chain you started), drop the dedicated database, and leave the shared
   `stockflow-postgres-test-1` service running.

Two details that cost time on the first run: React separates interpolated text with `<!-- -->`, so the
script strips those markers (`sed 's/<!-- -->//g'`) before matching visible text; and each run needs a fresh
SKU, because a soft-deleted SKU stays reserved and would turn the create step into a 409.

```bash
#!/usr/bin/env bash
set -u
BASE=http://localhost:3100
JAR=/tmp/t08-jar.txt
ORIGIN="Origin: $BASE"
JSON='content-type: application/json'
TEXT=/tmp/t08-text.html
FAILED=0
rm -f "$JAR"
RUN="$(date +%s)"
SKU="T08-LIVE-$RUN"
LC="$(printf %s "$SKU" | tr A-Z a-z)"
NAME="T08 live product $RUN"

# React splits interpolated text with <!-- --> markers: normalise before matching visible text.
status() { curl -s -o /tmp/t08-body -D /tmp/t08-head -w '%{http_code}' "$@"; sed 's/<!-- -->//g' /tmp/t08-body > "$TEXT"; }
loc() { awk 'tolower($1)=="location:" {print $2}' /tmp/t08-head | tr -d '\r' | tail -1; }
check() { if [ "$2" = "$3" ]; then printf 'PASS  %s = %s\n' "$1" "$3"; else printf 'FAIL  %s: expected %s got %s\n' "$1" "$2" "$3"; FAILED=1; fi; }
checkloc() { local l; l=$(loc); if [ "$2" = "$l" ]; then printf 'PASS  %s -> %s\n' "$1" "$l"; else printf 'FAIL  %s: expected %s got %s\n' "$1" "$2" "$l"; FAILED=1; fi; }
has() { if grep -qF -- "$2" "$TEXT"; then printf 'PASS  %s (contains %s)\n' "$1" "$2"; else printf 'FAIL  %s: body lacks %s\n' "$1" "$2"; FAILED=1; fi; }
hasnot() { if grep -qF -- "$2" "$TEXT"; then printf 'FAIL  %s: body has %s\n' "$1" "$2"; FAILED=1; else printf 'PASS  %s (no %s)\n' "$1" "$2"; fi; }

echo "== signed-out session checks (F5) =="
check "GET / signed out" 307 "$(status $BASE/)"; checkloc "GET /" /login
check "GET /products signed out" 307 "$(status $BASE/products)"; checkloc "GET /products" /login
check "GET /products/new signed out" 307 "$(status $BASE/products/new)"; checkloc "GET /products/new" /login
check "GET edit page signed out" 307 "$(status $BASE/products/11111111-1111-1111-1111-111111111111/edit)"; checkloc "edit page" /login
check "GET /api/products signed out" 401 "$(status $BASE/api/products)"
check "POST /api/products unauthenticated" 401 "$(status -X POST -H "$JSON" -d '{}' $BASE/api/products)"

echo "== sign in with the seeded demo credential (F1/N3) =="
check "POST /api/auth/login" 200 "$(status -c $JAR -H "$ORIGIN" -H "$JSON" -d '{"email":"demo@stockflow.local","password":"StockFlowDemo!2026"}' $BASE/api/auth/login)"
grep -c 'session_token' "$JAR" | sed 's/^/session cookies stored: /'

echo "== list, search, pagination, empty states (F2) =="
check "GET /products signed in" 200 "$(status -b $JAR -c $JAR $BASE/products)"
has "seeded SKU row" "DEMO-001"
has "seeded product name" "A4 copy paper"
has "money formatting" '$7.49'
has "range text" 'Showing 1–5 of 5'
has "pagination landmark" 'aria-label="Pagination"'
has "table header" 'Unit price'
check "search by SKU" 200 "$(status -b $JAR -c $JAR "$BASE/products?search=DEMO-002")"; has "search range text" 'Showing 1–1 of 1'; has "search hit" "Ballpoint pens"; hasnot "search excludes other rows" "A4 copy paper"
check "search by name" 200 "$(status -b $JAR -c $JAR "$BASE/products?search=copy%20paper")"; has "name search hit" "A4 copy paper"
check "literal % search" 200 "$(status -b $JAR -c $JAR "$BASE/products?search=%25")"; has "literal % empty state" "No products match"
check "no-match search" 200 "$(status -b $JAR -c $JAR "$BASE/products?search=zzz-nothing")"; has "empty state text" "No products match"; has "clear-search link" "Clear the search"
check "malformed page param" 200 "$(status -b $JAR -c $JAR "$BASE/products?page=abc")"; has "invalid query notice" "Those search parameters are not valid"
check "page=0 param" 200 "$(status -b $JAR -c $JAR "$BASE/products?page=0")"; has "page=0 notice" "Those search parameters are not valid"
# Streaming context: page-level redirect() is emitted as a client/meta redirect, so the status stays 200.
check "stale page beyond range" 200 "$(status -b $JAR -c $JAR "$BASE/products?page=2")"; has "streamed redirect instruction" 'NEXT_REDIRECT;replace;/products;307'; has "no-JS meta refresh" 'http-equiv="refresh" content="1;url=/products"'

echo "== create form and CRUD through the documented API (F2/F6) =="
check "GET /products/new" 200 "$(status -b $JAR -c $JAR $BASE/products/new)"; has "form price field" 'id="unitPrice"'; has "form submit label" "Create product"; has "form back link" "Back to products"
check "POST /api/products bad Origin" 403 "$(status -b $JAR -c $JAR -H 'Origin: http://evil.test' -H "$JSON" -d '{"sku":"x","name":"x","unitPrice":1,"quantityOnHand":1}' $BASE/api/products)"
check "POST /api/products" 201 "$(status -b $JAR -c $JAR -H "$ORIGIN" -H "$JSON" -d "{\"sku\":\"$LC\",\"name\":\"$NAME\",\"description\":\"created by the T08 live matrix\",\"unitPrice\":1234,\"quantityOnHand\":7}" $BASE/api/products)"
has "created DTO normalized SKU" "\"sku\":\"$SKU\""
ID=$(sed -n 's/.*"id":"\([0-9a-f-]*\)".*/\1/p' /tmp/t08-body | head -1)
printf 'created id: %s\n' "$ID"
if [ -z "$ID" ]; then echo "FAIL  create returned no id: later CRUD checks cannot run"; exit 1; fi
check "created row is listed" 200 "$(status -b $JAR -c $JAR "$BASE/products?search=$SKU")"; has "created row name" "$NAME"
check "GET edit page" 200 "$(status -b $JAR -c $JAR "$BASE/products/$ID/edit")"; has "price prefilled from cents" 'value="12.34"'; has "version hint" "Loaded version 0: saving sends this version"
check "PATCH stale version" 409 "$(status -b $JAR -c $JAR -X PATCH -H "$ORIGIN" -H "$JSON" -d '{"version":99,"name":"nope"}' $BASE/api/products/$ID)"; has "conflict code" "VERSION_CONFLICT"
check "PATCH current version" 200 "$(status -b $JAR -c $JAR -X PATCH -H "$ORIGIN" -H "$JSON" -d "{\"version\":0,\"sku\":\"$SKU\",\"name\":\"$NAME renamed\",\"description\":null,\"unitPrice\":4999,\"quantityOnHand\":3}" $BASE/api/products/$ID)"
check "GET edit page after save" 200 "$(status -b $JAR -c $JAR "$BASE/products/$ID/edit")"; has "saved name on form" "$NAME renamed"; has "saved price on form" 'value="49.99"'; has "version advanced" "Loaded version 1: saving sends this version"
check "DELETE current version" 204 "$(status -b $JAR -c $JAR -X DELETE -H "$ORIGIN" -H "$JSON" -d '{"version":1}' $BASE/api/products/$ID)"
check "deleted row gone" 200 "$(status -b $JAR -c $JAR "$BASE/products?search=$SKU")"; has "deleted empty state" "No products match"
check "second DELETE is 404" 404 "$(status -b $JAR -c $JAR -X DELETE -H "$ORIGIN" -H "$JSON" -d '{"version":1}' $BASE/api/products/$ID)"
# notFound() in a streamed response: 200 status per the not-found docs, correct 404 UI plus noindex.
check "unknown uuid edit page" 200 "$(status -b $JAR -c $JAR $BASE/products/00000000-0000-0000-0000-000000000000/edit)"; has "unknown uuid 404 UI" "Page not found"; has "unknown uuid noindex" 'name="robots" content="noindex"'
check "malformed id edit page" 200 "$(status -b $JAR -c $JAR $BASE/products/not-a-uuid/edit)"; has "malformed id 404 UI" "Page not found"

echo "== sign out revokes the rendered page (F5) =="
check "POST /api/auth/logout" 204 "$(status -b $JAR -c $JAR -H "$ORIGIN" -H "$JSON" -d '{}' $BASE/api/auth/logout)"
check "GET /products after logout" 307 "$(status -b $JAR -c $JAR $BASE/products)"; checkloc "products after logout" /login

echo
if [ "$FAILED" = 0 ]; then echo "MATRIX RESULT: all checks passed"; else echo "MATRIX RESULT: failures present"; fi
exit "$FAILED"
```

## 3. Architecture and mental model


### The boundary this task works inside

StockFlow is a Next.js App Router application where **pages are server components that authorize themselves and load data through services** (never through an HTTP self-fetch), and **client components only do what needs a browser**: typing, pending states, dialogs, and calls to the REST API. The invoice screens follow the exact shape T08 established for products, which is why they look like siblings:

```
   browser request                     server                              client
┌───────────────────────┐   ┌──────────────────────────────┐   ┌───────────────────────────────┐
│ GET /invoices         │──▶│ page.tsx                      │   │ (nothing until hydration)     │
│  (session cookie)     │   │  requirePageUser()  ── 307 ──▶ /login if signed out
│                       │   │  invoiceListSchema.safeParse  │   │                               │
│                       │   │  listInvoices(user.id, query) │   │                               │
│                       │   │   → { data, pagination }      │──▶│ InvoiceList (filter + table)   │
└───────────────────────┘   └──────────────────────────────┘   └───────────────────────────────┘

   form submit                         route handler                   service (Prisma)
┌───────────────────────┐   ┌──────────────────────────────┐   ┌───────────────────────────────┐
│ POST /api/invoices    │──▶│ app/api/invoices/route.ts     │──▶│ createInvoice                 │
│  {customer, dates,    │   │  requireAuth(headers)         │   │  snapshotItems → current price │
│   items:[…]}          │   │  assertSameOrigin(request)    │   │  calculateTotals(taxRateBps)  │
│ + cookie + Origin     │   │  readJson(createInvoiceSchema)│   │  invoice.create (one tx)      │
└───────────────────────┘   └──────────────────────────────┘   └───────────────────────────────┘
```

Three properties of that boundary drive most of the design decisions below:

1. **The server is the only validator.** The client pre-checks only what cannot be sent at all (an empty customer name, a non-whole quantity, no lines). Dates, ownership, stock, duplicates, arithmetic bounds and lifecycle legality stay in Zod schemas and services that are already covered by tests.
2. **Numbers cross the boundary as integer cents.** `lib/money.ts` is shared by server and client, so the preview and the saved totals cannot diverge by rounding — the same `calculateTotals` produces both.
3. **Money and stock only move on the server.** A draft reserves nothing; issuing deducts in one serializable transaction; cancelling restores once. The UI's job is to offer only legal actions and to show what the server decided.

### Component responsibilities

| Unit | Kind | Responsibility | Deliberately not its job |
|---|---|---|---|
| `app/(dashboard)/invoices/page.tsx` | server page | authorize, parse/validate `?status`/`?page`, load the owned page through the service, clamp a stale page | rendering rows or filtering client-side |
| `components/invoice-list.tsx` | client | status filter form (GET, works before hydration), table, badges, totals, pagination links, empty states | fetching data, knowing about stock |
| `app/(dashboard)/invoices/new/page.tsx` | server page | authorize, read `TAX_RATE_BPS`, compute the default dates on the server | any totals arithmetic |
| `components/invoice-form.tsx` | client | line set + metadata state, live preview, payload construction, server-error mapping, conflict recovery | recomputing tax rules or validating business rules |
| `components/product-picker.tsx` | client | paginated catalogue search/add at 20 rows per page with its own loading/error/empty states | knowing the invoice's line set (the form owns it) |
| `app/(dashboard)/invoices/[id]/page.tsx` | server page | authorize, validate the id before it reaches the uuid column, 404 on unknown/foreign, render snapshots, totals and the status meaning | deciding which actions are legal (it renders the service's current status; the client mirrors the transition table) |
| `app/(dashboard)/invoices/[id]/edit/page.tsx` | server page | same guards, then a draft-only gate: a non-draft redirects to the detail page | rendering a form that could never save |
| `components/invoice-actions.tsx` | client | the legal transitions with confirmations, pending state, 409/404 recovery, terminal-state note | inventing transitions (the server still refuses anything illegal) |

### The two state machines worth holding in your head

- **Invoice status** (owned by T07): `DRAFT → ISSUED | CANCELLED`, `ISSUED → PAID | CANCELLED`, `PAID`/`CANCELLED` terminal. `components/invoice-actions.tsx:36` mirrors that table *for rendering only*; every request is still guarded server-side by `version` and the current status.
- **Item set** (owned by T06): only a `DRAFT` may replace its items, the replacement is the whole set, `{version, items}` is the entire body, and lines already on the invoice keep their snapshot while new lines snapshot the current catalogue. The edit form's payload (`components/invoice-form.tsx:90`) is built to that contract exactly.

## 4. Implementation walkthrough

Every line number below is from the reviewed revision. The eight files are new; nothing else in the application changed.

### 4.1 `app/(dashboard)/invoices/page.tsx` — the list page (87 lines, server component)

Read it top-down: `metadata` (`:11`), a small URL builder (`:18`), then the page.

```ts
function invoicesHref(status: string | undefined, page: number): string {   // :18
  if (status) params.set("status", status);
  if (page > 1) params.set("page", String(page));
  return query ? `/invoices?${query}` : "/invoices";
}
```

The URL is the state, so page 1 and "all statuses" keep a short address and every list stays shareable — the same reasoning T08 used for `/products`. The page itself (`:32`):

1. `requirePageUser()` (`:33`) — per-page authorization; the shell's redirect is never the only guard.
2. Status normalization (`:36`): an empty `?status=` means "all statuses" (the filter's default option), so it normalizes to *absent* instead of a validation error; anything else is left for the schema to judge.
3. `invoiceListSchema.safeParse({ page?, status? })` (`:37`) — the API's own Zod schema validates the query, and because only those two keys are picked, unrelated query keys (bookmarks, tracking tags) cannot break the page. `pageSize` is deliberately not exposed.
4. Invalid input renders the header plus an explanatory `Alert` with a "Reset the list" link (`:52-69`) rather than a 500 — `?status=NOT_A_STATUS` and `?page=0` are user mistakes, not server failures.
5. `listInvoices(user.id, parsed.data)` (`:74`) is a direct service call: no HTTP self-fetch, no client round-trip, owner scoping inside the service.
6. A stale page is clamped (`:77-79`): if the requested page no longer exists (rows deleted, or the filter shrank the set) the page redirects to the last real page. Because the dashboard shell has already streamed, Next answers 200 and instructs the client to navigate — the framework behaviour T08 recorded as O3.
7. `InvoiceList` receives the server-rendered `Page<InvoiceSummaryDto>` and the committed filter (`:84`).

### 4.2 `components/invoice-list.tsx` — filter, table, pagination (145 lines, client)

- **Labels and colours** (`:20-42`): `STATUS_ORDER`, `STATUS_LABELS` and `statusVariant` map the API's uppercase union onto human labels and badge variants. The badge always renders its text, so colour is a secondary cue rather than the only one.
- **The filter** (`:50-74`) is a `next/form` `<Form action="/invoices">` wrapping a native `<select name="status">` (`:53-65`) plus a submit button and a Clear link. A GET form means the filter works before hydration and after a full reload, and the resulting address is shareable. `defaultValue={status ?? ""}` seeds the control from the URL — with the caveat recorded as **O1**.
- **Two empty states** (`:77-98`): filtered ("No draft invoices." + "Clear the filter") and never-created ("No invoices yet." + a "New invoice" button). Telling those apart is what makes an empty list actionable instead of looking broken.
- **Rows** (`:101-138`): number (monospace), customer, issue date, due date, badge, saved total with `tabular-nums`, and a View link whose `aria-label` names the invoice.
- **Pagination** (`:139`) reuses T04's `Pagination` with `basePath="/invoices"` and `query={{ status }}`; that component already drops empty values, so paging without a filter produces clean URLs.

### 4.3 `app/(dashboard)/invoices/new/page.tsx` — the create screen (34 lines, server)

`today()` (`:11`) returns a UTC `YYYY-MM-DD` string; `requirePageUser()` (`:20`) authorizes; `readEnv(process.env).taxRateBps` (`:21`) reads the configured tax rate **on the server**; the form receives `mode="create"`, that rate and the default date (`:31`).

Two deliberate details: the defaults are computed on the server so the server-rendered HTML and the hydrated client show the same value (a `new Date()` inside a client component is a hydration mismatch waiting to happen), and the tax rate crosses as an integer so the preview uses exactly the rate the service will persist. Nothing else from the environment reaches the browser.

### 4.4 `components/product-picker.tsx` — paginated catalogue search (245 lines, client)

This is the only invoice component that talks to the API directly, for one reason: the picker must reach **past the first page** of a large catalogue, so it pages `GET /api/products?search=&page=&pageSize=20`.

- `PAGE_SIZE = 20` (`:16`) and a `LoadedPage` record (`:28`) holding `{ key, result, failure }`.
- The effect (`:52-72`) is keyed by `requestKey = JSON.stringify([search, page, retryToken])` (`:47`), so "still loading" is *derived* (`loaded?.key !== requestKey`) rather than a second piece of state, and the effect only ever writes a **completed** answer. An `active` flag stops an out-of-order response from overwriting a newer one. (That shape is also what this repository's lint rule `react-hooks/set-state-in-effect` requires: no synchronous `setState` in an effect body.)
- `submitSearch` (`:74`) commits the typed text and resets to page 1; `clearSearch` (`:80`) restores the unfiltered first page.
- Rendering: search form (`:85-108`), the hint that paging covers the whole catalogue (`:110-112`), a failure `Alert` with "Try again" that bumps `retryToken` (`:114-124`), skeletons while loading (`:126-133`), the two empty states (`:135-158`), the results table (`:169-203`) where a product already on the invoice shows a disabled "Added" button, and the pager (`:212-232`) reporting "Showing 1–20 of N matching products".

Why a picker rather than a `<select>` of all products: the catalogue is paginated and can exceed 100 rows, and lines need per-line quantities — a searchable, pageable list is the smallest thing that satisfies F3 without loading everything or inventing an endpoint.

### 4.5 `components/invoice-form.tsx` — create and edit (562 lines, client)

The largest file, so read it in four bands: helpers, request builder, state/handlers, JSX.

**Band 1 — helpers (`:28-77`).**

| Helper | Line | What it is for |
|---|---|---|
| `fieldMessage(fields, path)` | `:34` | first server message for a path, e.g. `items.1.quantity` |
| `taxRateLabel(bps)` | `:39` | 1100 → "11%", 1105 → "11.05%" without float arithmetic |
| `linesFromInvoice(invoice)` | `:48` | seeds the editor from the **snapshots** the server returned, not today's prices |
| `previewOf(lines, taxRateBps)` | `:62` | wraps the shared `calculateTotals`: a line still being typed returns `null` (preview unavailable) instead of throwing |
| `withoutItemErrors(fields)` | `:76` | drops `items.*` messages when the line set changes |

`previewOf` is the reason the preview can be trusted not to drift: it calls the *same* `calculateTotals` the service calls, with the *same* integer cents and basis points, so the only way to differ is to send different inputs.

**Band 2 — the request builder (`:80-124`).** `buildRequest` returns `{ body }` or `{ errors: FieldErrors }` and deliberately checks only what cannot be sent:

```ts
input.lines.forEach((line, index) => {                                        // :97
  if (!/^\d+$/.test(line.quantity)) errors[`items.${index}.quantity`] = ["Enter a whole quantity of at least 1"];
});
if (input.lines.length === 0) errors.items = ["Add at least one product line"];

if (input.mode === "edit") {                                                  // :102
  return { body: { version: input.version, items } };                         // exactly the PUT contract
}
// create mode only: customerName non-empty, both dates present, notes trimmed-or-null
```

Everything else — real calendar dates, `dueDate >= issueDate`, stock, duplicate products, arithmetic bounds, ownership — is left to the server, which is the single validator. The edit branch is where the contract bites: `PUT /api/invoices/[id]/items` accepts exactly `{version, items}`, so no metadata is sent even though the form displays it.

**Band 3 — state and handlers (`:135-283`).** `InvoiceForm` is a discriminated union on `mode` (`:135`); in edit mode `taxRateBps` comes from the *persisted* draft (`:139`) so the preview keeps the rate the invoice was created with, even if `TAX_RATE_BPS` changed since.

- State (`:150-159`): `metadata`, `lines`, `version`, `pending`, `reloadPending`, `notice`, `failure`, `fieldErrors`, `reloadFailed`, `stale`. That is a lot of booleans, but each one renders a different recovery affordance; they are not interchangeable.
- `addProduct` (`:177`) appends `{ productId, productName, unitPrice, quantity: "1" }` from the **current** catalogue row and refuses duplicates; `updateQuantity` (`:186`) edits one string and clears only that line's message; `removeLine` (`:196`) drops the line and all `items.*` messages because indices shift.
- `applyInvoice` (`:201`) and `reloadLatest` (`:211`) implement version-conflict recovery: fetch the saved draft, replace the form state with it, and say so. If that fetch 404s, the form switches to `stale` and points at the list instead of looping.
- `handleSubmit` (`:233`) is the heart:

```ts
const built = buildRequest({ mode: props.mode, version, metadata, lines });   // :236
if ("errors" in built) { setFieldErrors(built.errors); setFailure("Check the highlighted fields and try again."); return; }
setPending(true);
try {
  if (invoiceId !== null) {                                                   // edit
    await apiFetch(`/api/invoices/${invoiceId}/items`, { method: "PUT", body: JSON.stringify(built.body) });
    router.push(`/invoices/${invoiceId}`);
  } else {                                                                    // create
    const created = await apiFetch("/api/invoices", { method: "POST", body: JSON.stringify(built.body) });
    router.push(`/invoices/${created.data.id}`);
  }
  // pending stays true: the button must not become clickable again while the page navigates
} catch (error) { /* 409/404/network mapping below */ }
```

  The `catch` (`:259-282`) is a small decision table: server `fields` go inline; `VERSION_CONFLICT` → `reloadLatest()`; `INVOICE_NOT_EDITABLE` → `stale` + the server's message; `404` *without* field errors → `stale` + "no longer exists"; everything else → the server's message, with the typed values still on screen. A non-`ApiClientError` (a bug, a thrown string) becomes "An unexpected error occurred" rather than leaking a stack trace into the UI.

**Band 4 — JSX (`:285-562`).** The metadata card (`:287-415`) renders inputs in create mode and a read-only `<dl>` in edit mode plus the sentence explaining that only lines are editable. The lines card (`:416-520`) holds the picker, an edit-mode hint about snapshots, the `items` array-level message, the line table with a quantity `Input` per row (`aria-label` includes the product name, `aria-invalid`/`aria-describedby` carry the server message), the preview `<dl>` of subtotal/tax/total, and the "Preview only…" note. The tail (`:522-560`) renders the notice, the failure alert (with a "View the invoice" link when `stale` and a "Load the latest saved lines" retry when a conflict reload failed) and the submit button whose label is "Create draft" / "Save draft lines" / "Saving…".

### 4.6 `app/(dashboard)/invoices/[id]/page.tsx` — the detail page (177 lines, server)

`STATUS_LABELS`, `STATUS_VARIANTS` and `STATUS_NOTES` (`:23-47`) and `taxRateLabel` (`:46`) are local copies — see O5 for why. Guards come first: session (`:61`), `domainIdSchema.safeParse` so a malformed id never reaches the uuid column (`:64`), `getInvoice` and a 404-to-`notFound()` translation (`:69-72`). The header (`:76-97`) shows the number, badge, customer and dates, plus the "Edit draft lines" button **only for a draft**. Then a status card explaining the stock consequence of the current state (`:99-107`), the lines table with its `TableFooter` totals (`:109-165`), and the actions card (`:167-174`).

### 4.7 `app/(dashboard)/invoices/[id]/edit/page.tsx` — the draft editor (59 lines, server)

Same three guards (`:27-37`), then the draft-only gate (`:41`):

```ts
if (invoice.status !== "DRAFT") redirect(`/invoices/${invoice.id}`);
```

An issued, paid or cancelled invoice has frozen lines and no route that can change them, so showing a form would be a lie. The redirect lands on the detail page, which states the current status; the live matrix confirmed the redirect marker and the absence of quantity inputs for an issued invoice.

### 4.8 `components/invoice-actions.tsx` — the status actions (234 lines, client)

`ACTIONS` (`:36-72`) is the transition table *for rendering*: DRAFT → Issue/Cancel, ISSUED → Mark paid/Cancel, PAID/CANCELLED → nothing. Each entry carries the label, the dialog title and a description that states the stock consequence in plain words. `run()` (`:109-139`) sends `PATCH /api/invoices/[id]/status` with the version that is currently on screen, sets a notice on success and refreshes the route so the new status, version and action set come from the server; a 409 refreshes immediately (the state that won should be visible), a 404 with field errors sets `lineFailure` (a line references a product that is gone → offer the editor), a transport failure keeps an explicit "Try again" for the same action. Terminal states return early (`:141-150`) with an `Alert` instead of dead buttons. The confirmations are a single controlled `AlertDialog` (`:205-231`) that stays open while the request runs (`event.preventDefault()`), so "Working…" is visible and every control is disabled — the F6 requirement made concrete.

### A concrete end-to-end path (the one the live matrix actually drove)

Assumptions: `TAX_RATE_BPS=1100`, two products at 1250 cents with 50 on hand, a signed-in user.

| Step | What the user does | What the browser sends | What comes back / changes |
|---|---|---|---|
| 1 | opens `/invoices/new` | `GET /invoices/new` + session cookie | server: session OK → reads tax 1100 → renders the form with today's dates; the picker then fetches `/api/products?page=1&pageSize=20` |
| 2 | searches "widget", clicks **Add line** on two products | two client-side `GET /api/products?search=widget&page=1&pageSize=20` requests | two lines appear, quantity 1 each; preview shows subtotal 2500, tax 275, total 2775 |
| 3 | sets quantities 2 and 3 | nothing yet | preview recomputes locally: 2500 + 3750 = **6250** subtotal, **688** tax (11% half-up), **6938** total |
| 4 | submits | `POST /api/invoices` + Origin + cookie, body `{customerName, issueDate, dueDate, notes, items:[{productId,quantity:2},{productId,quantity:3}]}` | 201 with the draft: `snapshotItems` copies name+price, `calculateTotals` stores 6250/688/6938, `version` 0; the form pushes to `/invoices/<id>` |
| 5 | reads the detail page | `GET /invoices/<id>` | the server renders the same 6250/688/6938 — preview and saved figures agree because both came from `calculateTotals` |
| 6 | clicks **Issue invoice**, confirms | `PATCH /api/invoices/<id>/status` `{version:0,status:"ISSUED"}` | the service claims the status in one transaction, deducts 2 and 3 and bumps both product versions; the detail refreshes as Issued, version 1; `/products` now shows 48 and 47 |
| 7 | clicks **Cancel invoice**, confirms | `PATCH … {version:1,status:"CANCELLED"}` | stock restored exactly once (50/50), status CANCELLED, actions replaced by the terminal note; that invoice's edit URL now redirects to the detail page |

The failure paths branching off this one are what the checklist exercises: overstock at step 4 (409 naming the product, message next to the line), the same draft open in two tabs (409 `VERSION_CONFLICT` → reload), a product deleted between steps 2 and 4 (404 on `items.N.productId`), and issuing a draft whose product was deleted (404 → "Edit the draft lines").

## 5. Correctness, edge cases and security

What the code actually defends, where that defence lives, and which task owns it if it breaks.

| Concern | How T09 handles it | Owner of the rule |
|---|---|---|
| **Authorization (F5)** | `requirePageUser()` in all four pages before any data access; the layout check is never relied on. A signed-out request gets 307 → `/login` (verified live on all four routes). | T04/T03 guard, T09 call sites |
| **Ownership** | pages pass `user.id` into services that scope every query; unknown **and** foreign ids both render the not-found state (verified live with a second user's cookie). | T05/T06/T07 services |
| **Snapshots** | the editor seeds from the server DTO (`linesFromInvoice`), the detail page renders stored values, and only *new* lines take current catalogue prices — the edit-mode hint says exactly that. | T06 retention rules |
| **Money precision** | integer cents throughout; the preview uses the shared `calculateTotals`, never float formatting; `formatMoney` only formats for display. | T02 `lib/money.ts` |
| **Tax rate** | create reads `TAX_RATE_BPS` server-side and passes an integer; an edit uses the rate persisted on the draft; the server recomputes from snapshots regardless of the client's numbers. | T02/T06 |
| **Version guards** | the loaded `version` travels with every edit and transition; `VERSION_CONFLICT` reloads the draft for a fresh decision instead of retrying blindly. | T06/T07 |
| **Stock effects** | the UI never computes stock; it offers only legal transitions, and a rejection (`INSUFFICIENT_STOCK`, `STOCK_OVERFLOW`) renders the server's message and refreshes. | T07 |
| **Lifecycle legality** | `ACTIONS` mirrors `assertTransition` for rendering only; the server remains the authority and a 409 refreshes the screen. Drift risk recorded as **O6**. | T07 |
| **Double submission (F6)** | `pending` disables every control (`disabled`, `aria-busy`), `handleSubmit` returns early while pending, and `pending` stays true through the post-save navigation; the dialog keeps its button disabled and reads "Working…". | T09 |
| **Transport failure (F6)** | `apiFetch` converts a thrown fetch into `status: 0` + `NETWORK_ERROR`; the form keeps typed values (the still-enabled submit button is the retry — see **O10**) and the actions component offers an explicit "Try again". | T04 helper, T09 usage |
| **Expired/revoked session** | any 401 from a protected endpoint makes `apiFetch` navigate to `/login`, so private content does not linger after revocation. | T04 helper |
| **Malformed/unknown ids** | `domainIdSchema.safeParse` runs before the value can reach the uuid column, and `AppError(404)` becomes `notFound()`; both render the same not-found state without revealing whether the invoice exists. | T02 contract, T09 usage |
| **Query-string abuse** | only `page` and `status` are read and both pass the API's strict Zod schema; an unknown status or an unsafe page renders the invalid-parameter state, and `pageSize` is not exposed at all. | T06 contract |
| **CSRF and origin** | untouched here: every mutating route already calls `assertSameOrigin`, and `apiFetch` sends cookies same-origin with a JSON content type. | T02/T03 |
| **Secrets** | the only environment value crossing to a client component is the integer tax rate; every other value stays server-side in `readEnv`. | T02 `lib/env.ts` |
| **Not applicable** | DB constraints, serializable retries, cleanup of iterators/streams, i18n, rate limiting — owned elsewhere and unchanged by this task. Marked so nothing above implies T09 implemented them. | — |

## 7. Limitations, observations and reviewer checkpoints

The skill asks for observed problems without repairing them. These are the findings from reviewing my own implementation against the card, the plan and the shipped contracts. **Nothing below was fixed**: the branch stays at the tested revision so the coordinator can rule on each one (T08's O1–O10 went through exactly this loop). The card carries the same list.

### Findings that are arguably defects

**O1 — the status `<select>` can display a stale value after a client-side URL change (`components/invoice-list.tsx:53-65`).** The control is uncontrolled with `defaultValue={status ?? ""}`. React 19 applies `defaultValue` for `<select>` on mount (`react-dom-client.development.js`, `case "select"` init path → `updateOptions(…, setDefaultSelected = true)`), and in the update path `setProp` explicitly ignores `defaultValue` (`case "defaultValue": break;`) while the select branch only calls `updateOptions` for a `value` prop or a `multiple`-presence change. My `defaultValue` is always *present* (it is `""` for "all"), so a change from `"ISSUED"` back to `""` — e.g. clicking **Clear**, or Back/Forward between two filtered addresses — is a present-to-present change that React does not push into the DOM. Predicted symptom: the dropdown keeps reading "Issued" while the rows show every invoice. It is cosmetic (the URL and the rows are right) and I could not confirm it here because no browser can start; **the reviewer should check it in row B2**. Fix if needed: `key={status ?? "all"}` on the `<select>` (remount) or make it controlled with `onChange` + `next/form`'s submit.

**O2 — the actions footnote says "Draft version N" on issued invoices (`components/invoice-actions.tsx:201`).** The paragraph renders for both DRAFT and ISSUED, so an issued invoice displays "Draft version 2: every action sends this version…". The number is correct and the sentence's point (the version travels with the action) is correct; only the word "Draft" is wrong. One-word fix: `Version {invoice.version}: …`. Left for the coordinator because it changes a file after the tested revision.

**O10 — the form has no dedicated retry control after a transport failure (`components/invoice-form.tsx:522-550`).** A network error shows the message and keeps the typed values, but the retry *is* the still-enabled submit button; unlike `invoice-actions.tsx`, there is no explicit "Try again". The card's phrase "transport failures keep a retry" is therefore looser than the code. Either the wording is tightened (my preference — one fewer control on a form that already has one) or a retry button is added.

### Findings that are documentation or consistency gaps, not defects

**O3 — the filter always submits `?status=`, even for "All statuses" (`components/invoice-list.tsx:53-65`).** Selecting the default option produces `/invoices?status=`, which the page then normalizes to "all" (`app/(dashboard)/invoices/page.tsx:36`). Harmless (and deliberately not an error), but the address carries a redundant parameter; a hidden empty-value guard or an `onChange` rewrite would keep addresses clean.

**O4 — the live matrix's coverage is narrower than the checklist's wording.** The matrix exercised DRAFT→ISSUED and DRAFT→CANCELLED end to end and asserted the ISSUED action set, but it never marked an invoice **PAID**, never executed any component JavaScript (no clicking, so the picker's Next/Previous and the dialogs are unproven by it), and asserted the active-navigation highlight only on `/invoices` rather than on all four routes. Those paths are code-reviewed (and PAID is API-tested by T07's transition matrix) but not live-executed. Checklist rows B2, C5 and D4 are where the reviewer closes the gap.

**O5 — labels, badge variants and `taxRateLabel` are duplicated across the client/server boundary.** `components/invoice-list.tsx:20-42` and `app/(dashboard)/invoices/[id]/page.tsx:23-52` each own a label/variant table, and `taxRateLabel` exists in both `components/invoice-form.tsx:39` and the detail page. This is forced by ownership: a shared module would need a graph-owned path, and `components/ui/**`/`lib/utils.ts` belong to T04. Maintainability only — a future shared-primitives task could collapse it.

**O6 — `ACTIONS` mirrors the service's transition table (`components/invoice-actions.tsx:36-72`).** If T07 ever adds or removes an edge, the buttons would offer the wrong set until the UI is updated (the server would still refuse illegal ones, so the failure mode is a confusing 409 rather than data damage). A comment says so; there is no test that can catch it, because no test path is owned here.

**O7 — a draft's customer, dates and notes cannot be corrected after creation.** `PUT /api/invoices/[id]/items` accepts exactly `{version, items}`, so the editor shows that metadata read-only and the only way to fix a typo in the customer name is to cancel the draft and create a new one. This follows the plan's contract (there is no metadata-update endpoint in the plan either), so it is a scope decision rather than a coding defect — but a reviewer will notice it, and a future task could add a metadata PATCH.

## Appendix B — the JSON helper and how the appendix was made durable

`/tmp/t09-json.js` is a four-line reader the matrix uses to pull fields out of API responses without jq:

```js
const fs = require("node:fs");
const [file, expression] = process.argv.slice(2);
const data = JSON.parse(fs.readFileSync(file, "utf8"));
const value = expression
  .split(".")
  .filter((key) => key.length > 0)
  .reduce((acc, key) => (acc === undefined || acc === null ? acc : acc[key]), data);
console.log(value === undefined || value === null ? "" : String(value));
```

## The big picture: T04 is the first task a human can *see*

T00 built the test infrastructure, T01 the database contract, T02 the vocabulary (schemas, DTOs, money, errors, origin, cookie forwarding), T03 the auth join. It adds no route handler, no table and no contract, so the question it answers is not "can a user register?" (T03 proved that through the real handlers) but: **"can a person actually reach that machinery, see what went wrong when it fails, get bounced when the session is gone — and can somebody else run the result from a fresh clone?"**

## Architecture and mental model

```
                         ┌────────────── browser ──────────────┐
                         │ /login   /register                  │
                         │ (any dashboard page added by T08/9) │
                         └───────┬──────────────────┬──────────┘
             client components   │                  │  server components
        ┌────────────────────────▼───────┐   ┌──────▼─────────────────────────┐
        │ components/auth-form.tsx       │   │ app/page.tsx                   │
        │ components/logout-button.tsx   │   │   requirePageUser() → redirect │
        │ components/pagination.tsx      │   │ app/(auth)/layout.tsx          │
        │   ↓ apiFetch()                 │   │   getSessionUser() → signed in?│
        │ lib/client-api.ts              │   │      redirect("/products")     │
        └────────┬───────────────────────┘   │ app/(dashboard)/layout.tsx     │
                 │ fetch, same-origin        │   requirePageUser() + nav      │
                 │                           │      + <LogoutButton />        │
                 │                           └──────┬─────────────────────────┘
                 │                                  │ lib/auth/session.ts (T03)
                 │                                  │ ── server-only ──
                 │                                  │ getAuth() → better-auth
                 │                                  │   → prismaAdapter → PG
                 └────────────► app/api/auth/*   (T03, unchanged)
                                app/api/products* (T05, unchanged)

   presentation layer (T04):  app/globals.css · components.json · lib/utils.ts
                              components/ui/* · components/{auth-form,logout-button,pagination}.tsx
```

Three boundaries carry the design:

- **`server-only` is the guard rail, not a convention.** The session helpers and everything behind them start with `import "server-only"`, so a client component that tries to import authorization breaks the build. T04's client code therefore reaches the server *only* through HTTP (`apiFetch`) — which is why the same helper will serve T08/T09 unchanged.
- **Neither a proxy nor a layout performs authorization.** The branch adds no root middleware/proxy; `app/page.tsx` and the two group layouts call `requirePageUser()`/`getSessionUser()` against the database. The card's rule is explicit — a layout is *never* the only authorization — so every data-bearing page below it repeats the check, which is the contract note T08/T09 inherit.
- **`lib/client-api.ts` is framework-free on purpose** (`lib/client-api.ts:69-76`): it imports no router, so the only way it can leave a page is a real `window.location.assign`. That is what makes an expired session stop rendering private content immediately, instead of negotiating with a client-side router cache.

The route surface at the pinned revision — verified live by this review through MCP `get_routes`, a `compile_route` call, and an independent `next build`: `/` (dynamic), `/_not-found` (static), `/login`, `/register`, `/api/auth/{register,login,logout,session}` (T03), `/api/products`, `/api/products/[id]` (T05), `/favicon.ico`. **`app/(dashboard)/` has a layout, a loading state and an error boundary but no page** — the single most important fact for anyone clicking around this revision.

## File-by-file walkthrough

### 1. The client seam — `lib/client-api.ts` (104 lines)

The only file in T04 with real logic, and the one the unit tests pin.

- `ApiClientError` (line 7) carries `status` and the parsed `body`, so a form reads `body.error.message` and `body.error.fields` instead of re-implementing response parsing.
- `errorBody()` (line 40) accepts *our* error envelope and sanitizes everything else: a proxy's HTML page, an empty body, JSON that isn't our shape all become `INTERNAL_ERROR`/`REQUEST_FAILED` with a safe message. **Why:** the UI must never render `undefined` or an HTML blob into an alert, and a client is the wrong place to discover the server broke its own contract.
- `readPayload()` (line 59) reads text and parses defensively, which turns "200 with `text/html`" into a typed `INVALID_RESPONSE` instead of a thrown `SyntaxError`.
- `navigateToLogin()` (line 69) is the session-expiry escape hatch; `isAuthEntryPoint()` (line 24) is the carve-out — **`/api/auth/login` and `/api/auth/register` keep their 401 inside the form**, because navigating away from `/login` after a rejected credential would discard the message the user needs (`lib/client-api.ts:18-23`).
- `apiFetch<T>()` (line 82) is the whole surface: same-origin credentials, `accept: application/json`, a JSON content-type for string bodies, `undefined` for 204, `ApiClientError` for every failure, and a network failure as `status: 0` + `NETWORK_ERROR` rather than an unhandled rejection. Caller headers survive (`new Headers(init.headers)`), so tracing keys or future auth headers need no change here.

### 2. The credential screens — `components/auth-form.tsx` (115 lines) and `app/(auth)/**`

One component serves both entry points (`mode: "login" | "register"`), because the two forms differ in wording, autocomplete hints and destination — not in mechanics.

- `handleSubmit` (line 38) posts `{email, password}` through `apiFetch`, then `router.replace(isRegister ? "/login?registered=1" : "/products")` (line 50). Both destinations are **fixed internal routes**: no return-URL parameter is read or honoured anywhere in T04, which removes an open-redirect class outright.
- Failures (lines 52-59) set a top-level message *and* the per-field map, so `fieldMessage()` renders "Password must contain at least 8 characters" beside the input with `aria-invalid` + `aria-describedby` (lines 75-83, 93-99). Values are never cleared on failure: re-typing an email after one bad password is exactly the friction this avoids.
- Pending state is triple-layered: `aria-busy={pending}` on the form (line 63), `disabled={pending}` on both inputs and the button, and an early `if (pending) return` (line 41) so a double click cannot produce two requests.
- The pages stay thin on purpose. `app/(auth)/layout.tsx:11-12` is the redirect — `getSessionUser(await headers())`, then `redirect("/products")` for a signed-in visitor — and it is a **database** read, so a stale cookie alone is not enough. `app/(auth)/login/page.tsx:13` awaits its `searchParams` Promise (the Next 16 shape) and shows the "Account created. Sign in to continue." status alert only for `?registered=1`; `app/(auth)/register/page.tsx` is a static shell.

### 3. The shell and its escape hatch — `app/(dashboard)/layout.tsx` (38 lines) and `components/logout-button.tsx` (42 lines)

- The layout calls `requirePageUser()` (line 11) purely to render navigation, prints `user.email` in the header, links to `/products`, `/invoices` and `/docs`, and mounts `<LogoutButton />` (line 32). Its own comment states the rule successors must keep: *"The session is validated here for navigation, and every page below repeats it before loading data: a layout is never the only authorization for private content."*
- `LogoutButton.handleLogout` (line 15) POSTs `{}` to `/api/auth/logout` — the T02 contract requires a JSON body, which is why a bare bodyless POST is a 400 — and only then performs `window.location.assign("/login")` (line 23). **Why a full navigation rather than `router.push`:** a client-side navigation may re-render cached server output that still belongs to the revoked session, whereas a hard navigation throws all of it away. A failure renders in a `role="alert"` span and the button becomes usable again (lines 33, 39).
- **Reachability caveat (review observation 3):** because T04 ships no page under `(dashboard)`, this layout never renders at the pinned revision, so the button is implemented but unreachable in a browser. The revocation underneath it was verified live instead — logout → 204, then the copied cookie → 401 — and the card's checklist row says exactly this ("After the dashboard shell renders (T08/T09)…").

### 4. Boundaries and metadata — `app/error.tsx`, `app/(dashboard)/error.tsx`, `app/not-found.tsx`, `app/layout.tsx`

- Both error boundaries take `{ error, retry }` — **`retry`, not `reset`**, the Next 16.3.5 signature — log through `useEffect`, and offer "Try again"; the root one adds "Go home". The dashboard boundary wraps its message in `<Alert variant="destructive">`. No page in T04 can throw deliberately, so these paths are wired-but-unexercised, and the card says so instead of claiming a pass.
- `app/not-found.tsx` renders the 404 with a working "Go home", which is what any unknown URL produces (verified: `GET /definitely-missing` → 404, title `Page not found · StockFlow`).
- `app/layout.tsx:6` sets `title: { default: "StockFlow", template: "%s · StockFlow" }`, so each page contributes only its own short `title` (`Sign in`, `Create account`, `Page not found` — all three confirmed in the served HTML). Fonts are **system stacks** declared in `globals.css`, so the build needs no network — a real constraint for the offline container build, not a style preference.

### 5. The design system — `app/globals.css` (89 lines), `components.json`, `lib/utils.ts`, `components/ui/*`

- `globals.css` follows the Tailwind v4 pattern: `@import "tailwindcss"` plus `@custom-variant dark`, a `:root`/`.dark` pair of OKLCH tokens (`--background`, `--primary`, `--destructive`, `--border`, `--ring`, …), an `@theme inline` block mapping them to utility names (`--color-*`, `--radius-*`) and to `--font-sans`/`--font-mono` built from the system stacks, and a base layer applying `bg-background text-foreground`. **Why it matters:** every kit component uses semantic classes (`bg-card`, `text-muted-foreground`), so T08/T09 can build screens without inventing colors, and a dark theme exists for free.
- `components.json` records the shadcn configuration (Tailwind v4 through `app/globals.css`, `@/` aliases, neutral base) while **the CLI itself is not installed** — the file is the contract for future hand-written additions, not a generator invocation.
- `lib/utils.ts` is the standard `cn()` (`clsx` + `twMerge`).
- `components/ui/*` — ten files, 471 lines total: `button` (variants + `asChild`), `input`, `label`, `textarea`, `table` (8 parts), `card` (6 parts), `badge`, `alert` (`Alert`/`AlertTitle`/`AlertDescription`, `role="alert"` overridable), `alert-dialog` (9 parts) and `skeleton`. Deliberately the *subset* the product and invoice screens will need, written against installed primitives only — no speculative components, no new dependency.

### 6. Shared pagination — `components/pagination.tsx` (69 lines)

`Pagination({ pagination, basePath, query })` is query-driven: `pageHref` (line 14) rebuilds the URL with the current filters preserved and omits `?page=1`, so the page number lives in the URL and every list stays shareable and server-renderable. It returns `null` when `total === 0` (line 28), so an empty list says "nothing here" through its own empty state rather than a pagination block claiming "page 1 of 1". `Previous`/`Next` degrade to disabled buttons at the ends instead of dead links, and the block is a `<nav aria-label="Pagination">` reporting "Showing X–Y of Z". Nothing renders it yet — T08/T09 consume it, which is why its props are documented in the card's contract table.

### 7. The container path — `Dockerfile` (34 lines), `.dockerignore` (20 lines), `docker/entrypoint.sh` (16 lines), `docker-compose.yml`

- The image is a single stage on `node:24.21.0-bookworm-slim` with `corepack prepare pnpm@12.4.2` — exactly the `mise.toml` pins, so the container cannot drift from local development. It installs the **full** dependency set rather than `--prod`, because the same image must run `prisma migrate deploy` and the `tsx` seed at start-up; the card records that as the accepted "keep it simple" trade-off. `openssl` is installed because Prisma warns and can mis-detect its engine on slim images (commit `f9f3bb9`).
- `COPY package.json pnpm-lock.yaml pnpm-workspace.yaml` before `COPY . .` keeps the dependency layer cacheable, and `.dockerignore` excludes `node_modules`, `.next`, `generated`, `.git`, `.env*`, docs and agent directories — a small build context and no path for a secret to enter the image.
- `docker/entrypoint.sh` validates `BETTER_AUTH_SECRET` **before touching the database** (empty, or still the `.env.example` placeholder → remediation message + `exit 1`), then `pnpm db:migrate`, then `NODE_ENV=development pnpm db:seed` (the seed refuses production by design, so the entrypoint overrides the mode for that one step), then `exec pnpm start`. **Why the ordering matters:** a fresh clone that forgot its secret fails loudly at start-up instead of booting a half-configured app that later 500s.
- The compose `app` service builds this image, waits for `postgres` to be *healthy*, and passes `DATABASE_URL` with the **service name** (`@postgres:5432`, not localhost), `BETTER_AUTH_SECRET` through compose's required-variable syntax (`:?`, so compose itself refuses to start without it), plus `BETTER_AUTH_URL`, `TAX_RATE_BPS` and `NODE_ENV=production`, publishing `3000:3000`. The existing `postgres` service keeps its `127.0.0.1:5432` mapping and named volume. The grader path is therefore: clone → `cp .env.example .env` → set a secret → `docker compose up`.

### 8. The Playwright removal and its harness tests — `scripts/test.ts`, `package.json`, `pnpm-lock.yaml`, `.gitignore`, `eslint.config.mjs`, `tests/unit/test-harness.test.ts`

Removing a test layer is a change to the *harness*, so it is pinned like one. `parseRunnerSubset` now accepts exactly `unit | integration`, the runner no longer branches on `e2e`, bare `pnpm test` runs two suites, and T00's configuration test `T00-H15` (which pinned `playwright.config.ts`, chromium, `workers: 1`, port 3100 and `reuseExistingServer: false`) is replaced by two tests:

- **T00-H24 — the retired layer is gone**: `playwright.config.ts` does not exist, `test:e2e` and `@playwright/test` are absent from the manifest, and the runner, `.gitignore` and eslint config contain no Playwright reference.
- **T00-H25 — the container contract**: `FROM node:24.21.0`, `pnpm@12.4.2`, an entrypoint running `db:migrate` + `db:seed` + `pnpm start`, and a compose file with an `app:` service on `3000:3000`, `condition: service_healthy` and a service-name `DATABASE_URL`.

**Why this is the right shape:** an amendment removes a capability, and an unpinned removal is exactly how capabilities quietly return. Two tests now make "no browser suite" and "the container starts a migrated app" properties of the repository rather than intentions. ## Happy path, traced end to end

This review ran the product path live in an isolated reviewer worktree at the pinned SHA, with its own dev database (`stockflow-postgres-1` on `127.0.0.1:5432`, migrated and seeded) and `pnpm dev --port 3100` (`BETTER_AUTH_URL=http://localhost:3100`).

1. **`GET /`** signed out → `307` to `/login`. `app/page.tsx` runs `requirePageUser()`, which reads the session from PostgreSQL through T03's guard and calls `redirect("/login")` when there is none — a fresh or revoked cookie behaves the same way.
2. **`GET /login`** → `200`, `<title>Sign in · StockFlow</title>`, two labelled inputs, a `noValidate` form with `aria-busy="false"`. `GET /register` → `200` with the "At least 8 characters" hint and `autocomplete="new-password"`.
3. **`POST /api/auth/register`** `{"email":"review-…@example.com","password":"ReviewPass!2026"}` with `Origin: http://localhost:3100` → **201** `{"data":{"id":"…","email":"review-…@example.com","name":"review-…"}}` and **no cookie** (T03's register revokes the session BetterAuth creates). The form then `router.replace`s to `/login?registered=1`, which renders the status alert.
4. **A rejected registration** (3-character password) → `422 VALIDATION_ERROR` with `fields.password`, so the screen shows the message beside the input and keeps the typed email. A duplicate email → `409 REGISTRATION_FAILED` ("Unable to register") — deliberately sanitized, so the screen cannot be used to enumerate accounts.
5. **`POST /api/auth/login`** wrong password / unknown email → **401** with a byte-identical `INVALID_CREDENTIALS` body, and the helper *does not* navigate for these two paths, so the message stays on screen. Correct credentials → **200** + the session cookie; a mismatched `Origin` → **403 ORIGIN_REJECTED** (verified separately).
6. **Landing:** the signed-in branch of `handleSubmit` sends the browser to `/products`. At this revision that route does not exist, so the user sees the **"Page not found"** boundary — documented as expected, and the reason the dashboard shell (and its Sign-out button) is not reachable yet.
7. **`GET /login` while signed in** → `307` to `/products` (the `(auth)` layout's database-backed check), and **`GET /api/auth/session`** with the cookie → `200` `{id,email,name}`.
8. **`POST /api/auth/logout`** with `{}` → **204**, and the same cookie afterwards → **401**: the session row is gone, which is the A3 behaviour T03 owns and T04's button triggers. (`GET /api/products` with the cookie returns the five seeded demo products — proof that T04's branch and T05's merged API coexist.)

Tooling paths, since there is no UI for them:

- **Local:** `pnpm install --frozen-lockfile` → `pnpm db:generate` → `pnpm db:migrate` → `pnpm db:seed` → `pnpm dev --port <leased>`; the app is served at `http://localhost:<port>` and every mutation requires that exact origin.
- **Container:** clone → `cp .env.example .env` → set `BETTER_AUTH_SECRET` → `docker compose up --build` → the entrypoint migrates, seeds and starts `next start` on `http://localhost:3000`.

## Correctness, edge cases and security

**Applied and verified in this review**

- **No open redirect.** Both credential screens navigate to hard-coded internal paths; no `redirect`/`returnUrl`/`next` parameter is read anywhere in T04's new files.
- **Session truth is the database, not the cookie.** `/`, `/login` and `/register` all resolve the session server-side, so a revoked session redirects on the next request; the client helper's 401 → `/login` navigation is the client-side half of the same property (unit-tested, including the "no `window` present" no-op case).
- **Errors are safe to render.** Unexpected shapes and 5xx-like bodies become generic codes; the only detail that reaches the screen is what T02's error contract deliberately exposes (code, message, field paths).
- **Origin enforcement is inherited, not re-implemented.** T03's routes assert exact origin before parsing the body; T04's forms add no bypass, and this review reproduced `403 ORIGIN_REJECTED` from a foreign `Origin`.
- **No secret reaches the client.** T04 adds no `NEXT_PUBLIC_*` variable and no client-side import of `lib/env.ts`/`lib/auth/*` (the `server-only` guard would break the build), and the container validates the secret before migrating.
- **Accessibility is part of the contract, not decoration:** labelled inputs with `aria-describedby` error text, `aria-busy` on both forms, `role="alert"` failures, `role="status"` for the registration notice, `aria-label` on the pagination nav, and an `sr-only` "Loading…" with `aria-live` on the skeleton.
- **Test characterisation:** 10 unit cases pin the helper's success/error/session-expiry behaviour; two harness cases pin the Playwright removal and the container contract. Everything else about T04 is *checklist* evidence, by decision.

**Where the residual risk actually lives**

- **The logout click path is unreachable at this revision** (no dashboard page), so it is verified only at the API level plus the merged integration suite, and its failure branch ("Sign out failed, try again") is unexercised in a browser. ## The transferable lessons

1. **Removing a capability is a change you test, not a deletion you hope nobody notices.** Deleting Playwright was pinned by two harness tests (`T00-H24`, `T00-H25`) and a new red phase. An unpinned removal is how a retired capability quietly returns six tasks later.
2. **When the verification tool is unavailable, change *how* you verify — and say so out loud.** With no browser runner and no way to install one, T04 moved F1/F5/F6 from "browser-asserted" to "checklist-verified at review time", published the checklist on the card, and kept the parts that *are* cheaply testable under unit tests. That is honest engineering; silently dropping the evidence requirement would not be.
3. **UI needs one seam you can unit-test, and a written procedure for everything else.** Here the seam is `lib/client-api.ts` — status codes, field errors, 401 carve-outs, 204, non-JSON bodies — and the procedure is the reviewer checklist. Ten tests plus fifteen checklist rows cover more ground than a dozen brittle DOM assertions would.
4. **Authorization is a database read, never a cookie's opinion and never a layout's side effect.** `/`, `(auth)/layout` and `(dashboard)/layout` all resolve the session server-side, and the dashboard layout's comment says plainly that it is not authorization for the page beneath it. Coding that rule into the comment is what stops the next task from leaning on the shell.
5. **A framework-free client helper is a feature.** Because `apiFetch` cannot reach a router, an expired session cannot be "handled" by a soft navigation that keeps stale server output on screen. Constraining the tool made the correct behaviour the only behaviour.
6. **Keep the error where the user is looking.** Exempting the two credential endpoints from the 401 → `/login` redirect is a two-line carve-out that prevents the single most annoying auth bug: the form that redirects away from its own error message.
7. **Put list state in the URL.** Query-driven pagination (`?page=n`, filters preserved, page 1 implicit) keeps every list shareable and makes the server render the truth; a pagination block that returns `null` on an empty result keeps the empty state honest.
8. **Define tokens before screens.** Because `globals.css` exposes semantic OKLCH tokens and the kit uses them, T08/T09 can build product and invoice pages without inventing styles — and the system-font stacks mean the build never needs the network, which a fresh-clone container build silently depends on.
9. **A container that checks its own prerequisites turns a silent misconfiguration into a loud failure.** Validating `BETTER_AUTH_SECRET` (including "still the example placeholder") before migrating means a fresh clone either works or tells you exactly what to set.
10. **"Implemented but not exercisable" is a real state, and it must be recorded as one.** The logout button, the error boundaries and F5's "every dashboard page" all exist and all lack a reachable page at this revision. Naming that state — and telling T10 how to word it — is what keeps the ledger truthful instead of optimistically green.
11. **Keep the verification environment separate and prove the separation.** This review ran in its own worktree with its own database, and the MCP bridge reported `projectPath` = that worktree. "The dev server is mine and scoped to my revision" is checkable, not assumed.
